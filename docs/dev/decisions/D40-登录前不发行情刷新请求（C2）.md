# D40 · 登录前不发行情刷新请求（**C2**）

> **决策号**：D40 · **日期**：2026-09-29 · **级别**：**C2**（人工拍板，命中 §8.1 红线 3「反转已交付行为」）

> **关联**：`docs/dev/0.1.1-使用反馈.md §7`（原始提问）· `docs/dev/STATUS.md` · `task-breakdown M14/T14.9` · 用户指南 §5.8

## 1. 背景（现状与问题）

**现状（人工实测 + 代码核实）**：应用**启动即联网刷新行情**，与是否登录无关——
`Main.kt` 启动路径直接 `scheduler.refreshMarketNow(manual = false)`；`BackgroundScheduler.start()` 在组合期启动并按间隔刷新；
托盘「立即刷新行情」在登录页同样可点且会真实发请求。自选清单是**全局设置行** `settings.watch.coins`，
故「未登录也知道要刷哪些币」⇒ 人工质疑「未登录就外联」的合理性。

## 2. 拍板结论

**行情刷新（CoinGecko / CoinMarketCap）一律以「会话已解锁」为前提**：

| 时机 | 登录前 | 登录后 |
|---|---|---|
| 启动首次刷新 | **不发**（跳过） | 登录成功后**立即补刷一次** |
| 后台周期刷新 | **不发**（跳过本轮，不排队补发） | 按间隔正常刷新 |
| 托盘「立即刷新行情」 | **不发**；给出「请先登录」提示 | 正常执行 |
| 登出 / 切换账户 | 立即停止刷新；切换后按新账户重新开始 | — |

**范围界定**：本决策**只约束行情刷新**（两类独立 API 中的行情侧，`§1.1-4`）。
交易数据同步（交易所只读 API）**不在本决策范围内**——其登录前行为维持现状（无 Key 时自然失败并提示），
如需一并收口另开决策（见 §6）。
