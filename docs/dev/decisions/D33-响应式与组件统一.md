## 1. 背景

第七轮人工走查在**三档分辨率**（1024×768 / 1280×800 / 2560×1600）上暴露 8 条问题，逐条查根因后发现它们**同源**：

| 现象 | 根因（共性） |
|------|--------------|
| 2560×1600 币种列第三枚徽标被裁 | 表格列宽用**固定 `weight`** 分配 → 不保证每列 ≥ 其内容最小宽 |
| 1024×768 卡片大数字换行变形、环形图图例币种名换行 | 大号数字/名称**无单行约束**，被压窄即折行 |
| 交易表手续费换行、滚到最右删除按钮只有一半 | 单元格**漏加**单行约束；纵向滚动条**画在最右缘压住最后一列** |
| 交易/增资表单弹窗总有「不到一行」的滚动条 | 弹窗内容高度上限**写死**（470/420dp），与窗口高度无关 |
| 截断数据悬停看不到全值 | 截断后**无查看全值途径**（财务数值不可核对） |
| 各页列表无单元线 | 缺少统一的列表可读性规范 |

即：**同一类问题在多个页面反复出现**，各页各自 `Row + weight`、各自写卡片、各自定弹窗高度——
没有统一的「表格 / 卡片 / 弹窗 / 断点」组件与规范。人工的追问因此不是「再修一次」，而是**要不要建体系统一**。

**关键事实（诊断结论）**：Windows 显示缩放会显著缩小**有效 dp 宽度**（2560×1600 @200% ≈ 1280dp 可用空间），
所以「宽屏」在应用看来仍是窄窗——断点必须按**内容区有效宽度 dp** 判定，而不是物理分辨率。

## 2. 拍板结论（C1）

### 2.1 三层结构：断点 → 组件 → 页面

1. **断点（唯一来源）**：`ui/theme/Breakpoints.kt` 的 `WzWindowClass`（COMPACT < 1200dp ≤ MEDIUM < 1760dp ≤ WIDE，
   按内容区有效宽度）；由 `MainShell` 经 `ProvideWzWindowClass` 下发，页面经 `LocalWzWindowClass` 读取，
   **禁止各页面自行判断窗口大小**。
2. **统一表格**：`ui/components/AdaptiveTable.kt`（唯一数据表实现）——
   - 列宽 = 最小宽 + 弹性（`TableColumn.flex` 默认 = `minWidth.value`）：可用宽 ≥ Σ最小宽时**按最小宽比例**分配
     （等价于保证每列 ≥ 自身最小宽）；否则整表横向滚动、列取最小宽；
   - 单元格一律 `SingleLineText`（单行 + 省略号 + **截断悬停显示全值**）；徽标单行且**与主文本内联**；
   - **单元线**（`divider`，默认开）；操作列一等公民（`TableWidths.ACTIONS = 120dp`）；
   - 列表区右侧预留 **12dp 滚动条槽**（纵向滚动条不得压住最右列）。
3. **统一卡片**：`ui/components/WzCard.kt` —— `WzCard` / `WzCardLabel` / **`WzMetric`（指标数字单行 + 自动缩字号，
   下限 0.68×，绝不换行）** / `SingleLineText` / `rowDivider` / `HoverTooltip`。
4. **弹窗尺寸策略**：`modalContentMaxHeight()` = 窗口高 × 0.66（下限 320dp），替代写死上限；表单内边距紧凑化。
5. **列表可读性**：表格行由组件提供单元线；非表格列表用 `rowDivider()`（1px `line` 色、最低强调）。
