## 1. 口径变化（D37 → D38）

| 维度 | D37（上一轮） | **D38（本档，现行）** |
|------|--------------|----------------------|
| 配色 | 自建 12 token 手写 hex，**翻译**成 M3 role | **M3 官方算法生成**：品牌种子色 `#1F5A48` → HCT 色调板 → `SchemeTonalSpot` → 全部 role（浅色 + 深色共用同一种子）；生成物 `M3ColorRoles.kt`（**勿手改**） |
| 字体 | 自建 10 档（14/20/27/32…） | **M3 15 档 type scale 规范值**（display 57/45/36 · headline 32/28/24 · title 22/16/14 · body 16/14/12 · label 14/12/11 + 行高/字距/字重）；业务槽位由其**投影** |
| 圆角 | 自建 4/7/10/14/20 | **M3 规范阶梯 4/8/12/16/28**（`ShapeTokens`），并**收敛全仓 13 个文件里散落的 60 余处硬编码圆角** |
| 动效 | 自建 120/200/320ms + 3 曲线 | **M3 motion tokens**：16 档时长（short1–4 / medium1–4 / long1–4 / extraLong1–4）+ 6 条标准曲线 |
| 组件 | 仅按钮/输入/日期时间换成官方 | **原则确立：凡 M3 有对应组件的一律用官方**（表格因 M3 无 DataTable 例外，见 §3） |
| 对比度 | `ContrastTest` 守护 | 增加**生成期自检**（`generate-m3-color-scheme.mjs` 内置 WCAG 校验，不达标直接生成失败） |

**保留的产品身份**（M3 规范未约束的部分）：字体族（数字用衬线、表格数字用等宽）、
盈亏/警示语义色（M3 无 gain/loss/warn role，按同一套色调板算法派生）、
品牌种子色（墨绿）、桌面数据密集档（正文取 M3 **bodyMedium 14** 而非触屏默认 bodyLarge 16）。

## 2. 关键决策点

1. **种子色 = 浅色与深色共用同一个**（M3 规范口径）。副作用：深色主题强调色由原「黄铜」变为算法输出的浅绿
   （`#89D6B9`）。若人工希望深色保留黄铜，只需改脚本 `SEED` 并重跑（一行命令，见 `docs/tech/dev-setup.md`）。
2. **`error` role 固定**（不再随盈亏配色方案翻转）——原先 `error = loss`，切到「红涨绿跌」时表单校验红字会变绿，属语义错误。
3. **表格文字档位**：数据表用 M3 `bodyMedium`(14)/`labelMedium`(12) 而非 bodyLarge(16)——桌面数据密度所需，
   且 14/12 都是 **M3 规范档位**（不是自定字号）。
4. **不引入任何第三方依赖**：配色生成用 Google 官方 npm 包，**仅生成期使用**，产物为 Kotlin 常量。

## 3. 与 M3 规范的**例外清单**（必须在文档里可见）

| 例外 | 原因 | 处置 |
|------|------|------|
| 数据表格 | ✅ 已核实 M3 / Jewel / Carbon / Fluent **均无 DataTable** | 保留自研 `AdaptiveTable`（D33），列宽/单行/截断/单元线口径不变；视觉 token 全部走 M3 |
| 盈亏/警示色（gain/loss/warn） | M3 只有 `error`，无盈亏语义 | 按 M3 色调板算法从三个语义种子派生（浅色 tone 40 / 暗色 tone 80），生成期校验 ≥4.5:1 |
| 应用内弹层（`WzModal`） | `AGENTS.md §7.3-①`：官方 `Dialog`/`Popup` 承载交互在本项目实测不可靠 | 保留同窗口就地叠加层；**内部内容**（日期选择器/按钮/输入框）一律用官方组件 |
| M3 Expressive motion scheme | ✅ 实测：`MotionScheme` 与 `MaterialTheme(motionScheme=)` 在 material3 **1.9.0 仍为 internal** | 自绘组件用 M3 token 数值（同源）；待上游公开后补一行接线 |

## 6. 遗留与下一步

1. **原型 HTML 与实现已不一致**（M3 规范取代 P1 的暖纸手绘基准）→ 显式延期到 **T14.5**（到期检查点 = M14 收尾轮），
   产出方式建议：以应用实际截图 + M3 token 表**替换**原型作为 P4/P6 视觉基准（需人工拍板是否保留 HTML 原型形态）。
2. `WzSelect` 触发框 → M3 `ExposedDropdownMenu`、`WzToast` → M3 `Snackbar`（T14.3 尾项）。
3. `WzCard`/`WzStatusBar`/`WzTable` 的容器视觉可进一步向 M3（filled/elevated/outlined 三态 + 容器色阶）收敛。
4. 人工 GUI 走查（双主题 × 三档分辨率 + 键盘/IME）——**本档的最大风险是"观感是否可接受"**，必须目视拍板。

## 7. 人工提问的答复：「0.2.0 是新里程碑，还是现有的维护？」

**是新迭代（新里程碑），不是现有版本的维护。** 三点澄清：

1. **里程碑层面**：P4 的 **M0–M13 已全部通过并交付**（0.1.x）；本轮新增 **M14「UI 体系统一」** 作为 **P8 下一迭代**的内容，
   与 M0–M13 并列而不覆盖。任务号 **T14.1–T14.7**（见 `task-breakdown.md §1/§3`）。
2. **代码层面**：**不做重写**——复用现有四模块结构、全部数据/领域/数据层，
   **零数据模型改动、零接口签名改动、零加密/备份改动**；改动集中在 `ui/theme`、`ui/components` 与各页面的取色/取字/取圆角处。
   属 `§8.1` 红线 3 意义上的「**已通过模块的表现层返工**」⇒ 级别 **C2**，走 §8.3 mini 闭环（需求→设计→技术→返工→人工门），**不重跑全局 P1/P2**。
3. **版本层面**：
   - **0.1.x = 维护线**（补丁：缺陷修复，如已并入的 DEF-54/55/56；语义化版本 patch）；
   - **0.2.0 = 本次迭代**（minor：视觉与组件基线变更，0.x 语义下允许破坏性的观感/交互变化）；
   - 发布路径不变：**P6 全量复测 → 人工门 → P7 发布 0.2.0**。
