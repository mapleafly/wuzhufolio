- 对比度：沿用 T0.6 的 `ContrastTest` 双主题 7 token × 2 底 ≥4.5:1 守护（本模块新增色仅环形图
  palette，取自原型且在明暗两档各有对应；不与文本底色直接相邻，不参与文本对比度判定）。
- **读屏（NVDA/JAWS）实测**仍受 ADR-001 风险约束（Compose Desktop 读屏支持弱于 Web），
  留 P6 系统测试登记执行——见 §5-2。

### 1.5 T12.4 全量 i18n（zh/en）

- **资源层**：`ui/i18n/` 新增 10 个文案目录（Common/Shell/Market/Ledger/Auth/Settings/Backup/Exchange/
  Gallery/Portfolio）+ `I18n`（语言持有器）+ `WzFormat`（数值/时间格式化），共 ~3700 行。
- **既有 `*Copy` 门面保持调用点零改动**：全部 `const val` 改写为**动态取值属性**
  （`val X: String get() = xxxStrings.x`），成员名与签名逐一保留——这是本模块能不动 700+ 调用点
  完成全量 i18n 的关键（约定见 `CommonStrings.kt` 头注 4 条规则）。
- **语言切换即时生效**：`WuzhuTheme(language = …)` 同步持有器 + `key(language.code, precision)` 强制
  整棵子树重建（文案是普通属性而非 Compose State，这是唯一可靠的重组触发点，函数头注已写明）。
- **语言入口**：设置 → 通用 → 「界面语言」（中文 / English，语言名用本语言书写），
  与主题/盈亏配色同路（`ShellViewModel` → `settings` 全局行 **`locale`**），持久化并在下次启动生效。
  对应 C1 决策档 **D25**（含影响面扫描与下游回写清单）。
- **精度消费**：`WzFormat.precision`（8/2/2 与 2/2/2 两档）由设置驱动，主题按精度档重组；
  **微小价格自适应**（有效数字不足时自动增加有效数字位，避免显示为 0，PRD「数据精度」）。
- **小额阈值消费**：仪表盘环形图「其他」归并（阈值 0 = 不启用）。
- **多法币/时间**：金额前缀随基础法币（USD → `$`，其余 ISO 前缀）；时间**时区恒为系统本地**、
  **格式随语言**（zh `2026-09-10 15:24` / en `Sep 10, 2026 15:24`）。
- **守护测试**：`I18nCatalogTest` 三查——双档非空、en 档零 CJK、**`ui/src/main` 除 i18n 目录外
  不得再出现中文字符串字面量**（注释先剥离；KDoc 按项目约定仍为中文）。此后新增页面若漏抽文案，
  测试直接红灯。

### 1.6 M11 §6 交接四项打磨（闭环）

1. **状态栏数据源/额度/429 文案** → 新增 `ShellStatusViewModel`（§1.3）。

### 1.7 勘误（C0，无独立决策档）

- **`CoinResolutionException` 增类型化 `kind`**：UI 原以 `reason.contains("歧义")` 判分支——
  界面逻辑绑在数据层中文正文上，且 en 档无法独立成句。新增 `CoinResolutionKind`
  （AMBIGUOUS/NOT_FOUND/FIAT_UNSUPPORTED/CANDIDATE_GONE/UNKNOWN，默认 UNKNOWN 兼容既有构造），
  data 层 9 处抛出点带上类型；zh 档文案**逐字不变**（仍用 `reason` 正文，含候选数），
  en 档按 `kind` 成句。属实现偏差纠正，不改产品语义 → C0。
- **`MarketCopy.WATCH_EMPTY` 文案订正**：原为「自选为空 · 用上方搜索添加币种」，
  与 interaction.md §2.7 及原型「暂无自选，搜索添加币种」不一致 → 以文档/原型为准订正（C0）。
- **detekt 配置补齐测试目录排除**：为 i18n 目录加 `MaxLineLength`/`TooManyFunctions` 例外时，
  显式 `excludes` 会**覆盖** detekt 默认的 `**/test/**` 排除，导致测试类被误判（每用例一函数
  ≥11 即触发）。已在配置中显式带回默认测试排除并加注说明。

### 7.2 走查问询 1–4 的复算结论（真实开发库，账户 Alex）

复算方式：复制真实数据目录到临时目录（**绝不触碰原库**），用真实服务链路
（`LedgerEventAssembler` → `ReplayEngine` → `PortfolioCalculator` → `DefaultPortfolioService`）
逐事件重放并打印轨迹；一次性诊断夹具用完即删（未入库）。

**共同根因（一件事）**：该账户的账本只有 Binance 成交切片（2022-11 起 117 笔），
**几乎没有入金记录**（`capital_flows` 仅 1 笔 1 USDT），早期持仓也不在账内。于是：
计价腿（USDT）与部分币种被反复打成负持仓，而**引擎在负区间仍继续累积成本**，
待持仓被买回正数时，累计成本被摊到远小于它的数量上 → **平均成本失真** →
其后每一次卖出的已实现盈亏都被这个失真成本放大。

**Q1「累计已实现盈亏 28819.65 是不是亏损」**：是**亏损**（卡片按 `+/-` 强制符号显示为 `-28,819.65`）。
口径 = Σ 每笔卖出 `[(卖出腿折算 − 手续费折算) − 卖出数量 × 该笔卖出时的平均成本]`。
但**本账户的这个数不可信**：−28,819.65 中 −28,691.84（99.6%）来自 BTC，而 BTC 平均成本被抬到
125,176.63（真实买入价 16k–67k）。

**Q2「ROI 非常高是计算问题还是数据问题」**：**数据问题，公式无误**。
ROI = (净值 + 累计撤资 − 累计增资) ÷ 累计增资 × 100%；本账户 累计增资 = **0.999576**
（只记录了 1 USDT 入金），净值 55,381.41 → ROI ≈ **5,540,390%**。
PRD 只规定「累计增资 = 0 时显示 --」，此处分母 = 1 故照常计算。**补录真实入金后 ROI 才具意义**。

**Q3「USDT 平均成本 1.48 怎么来的」**：`平均成本 = 成本 ÷ 数量`，而 USDT 的成本池被负区间污染。
轨迹（引擎实测）：2022-11 起买入不断支出 USDT 却从无入金 → 2024-03 已 −21,278；
负区间里每次卖出仍按 `cost += legFiat` 累积成本（此时 21,721.99），
2024-07-24T10:10 卖出把持仓拉回 +2,512.06 时，**成本 28,365.64 被摊到 2,512 个币上 → 均价 11.29**；
此后卖出持续按 1:1 稀释（4.74 → 3.80 → 2.62 …），最终停在 **1.4874**。

**Q4「BTC 卖出列表：有的有已实现、有的没有、有一个 −5784347」**：
- **没有值的**：该笔卖出发生时 BTC 持仓 ≤ 0 —— 引擎明文规则「异常区段不推导已实现盈亏（无成本基数）」，
  界面显示 `--`（2024-07-26 的五笔即属此类）。
- **−57,843.47 那笔**（2025-02-02 16:21:32，0.06443 BTC @99,246.80，实测值 = `-57843.46664686…`）：
  此时均价因 2025-01-10 的手动补买（0.2 BTC @50,000 记在 −0.18997 的空头上）被抬到
  **997,018.94**，故 `已实现 = (6,394.47 − 0.0075) − 0.06443 × 997,018.94 = −57,843.47`。
- 计算方式（与交易管理页同源，`SellRealizedTracer`，引擎合计交叉校验）：
  `已实现 = (卖出腿折算值 − 手续费折算值) − 卖出数量 × 卖出时平均成本`；
  平均成本 = 成本/数量，成本按比例移出（均价不变）。

**处置建议（给人工）**：该账户应在「资金管理」补录真实入金（以及早期持仓的增资/校准），
补录后重放会把平均成本与已实现盈亏拉回可信区间；期间界面已用「成本不可靠」徽标明确提示（§7.1）。

### 7.4 提报：引擎在负持仓区间的成本累积缺陷（**C2 候选，本模块未改**）

**现象**：持仓在负区间时，引擎继续累积成本；持仓回到正数后，这些"无对应数量"的成本被摊到剩余数量上，
使**平均成本与之后所有卖出的已实现盈亏失真**（实测：BTC 均价被抬到 997,018、USDT 均价 1.4874、
单笔卖出已实现 −57,843.47，而真实交易是获利的）。

**代码位置**：`domain/engine/ReplayEngine.kt`
—— `applyTrade` 的 SELL 分支 `quote.cost += e.legFiat`、BUY 分支 `base.cost += e.legFiat + e.feeFiat`
在持仓 ≤ 0 时仍执行；`reducePosition` 仅在数量 > 0 时按比例移出成本（成本不会为负），
**但没有任何一步把「已归零/转负的持仓」的成本同步归零**。

**现状口径**：引擎 KDoc 只声明「异常区段不推导已实现盈亏（无成本基数）」，未声明恢复后的成本如何重建；
`CoinHolding.hadNegativeBoundary` / `ReplayOutcome.violations` 记录了边界，但没有参与成本修正。

**影响面**：所有「导入账本缺入金/缺早期持仓」的账户（API 同步 + CSV 导入的常见形态）——
平均成本、浮动盈亏、已实现盈亏、ROI 全部失真，且此前**界面无任何提示**（本轮已加「成本不可靠」标注兜底）。

**✅ 人工拍板（2026-09-11）**：**「拍板选甲」** —— 决策档 `docs/dev/decisions/D26-负持仓区间成本口径.md`（C2），
