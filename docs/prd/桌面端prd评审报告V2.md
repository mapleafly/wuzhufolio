## 一、评审结论摘要

**总体判断：V1.2 相较 V1.0 有质的提升，上一轮 6 个 🔴 级硬伤（ROI 公式、现金余额模型、24h 盈亏、密钥架构矛盾、三源去重、版本混乱）全部得到解决，文档已接近开发基线水平。但修订过程中引入了 3 个新的系统性问题，建议在冻结基线前完成最后一轮修订。**

亮点（本轮新增）：

- ROI 改为「总收益 / 累计增资」口径后数学上自洽，撤资场景不再失真（L36-38），且明确标注了「简化资金加权、不含时间加权」的 MVP 局限，分寸感好。
- 「单一持仓账本」模型（现金 = 法币 + 稳定币白名单持仓的派生聚合，不单独记账）彻底闭合了上一轮的现金流断裂问题，并顺带解决了饼图与总资产口径不一致的问题（U8 自然消解）。
- 交易联动规则（买入扣 quote、余额不足阻止保存、手续费三币种处理）写得足够细，开发可直接照做（L344-347）。
- DEK/KEK/GCM/KDF 分层密钥 + OS 钥匙串会话令牌 + 严格模式切换，安全设计已达到可评审深度。

本轮发现的系统性问题（按严重度排序，详见第三节）：

1. **成功指标与「无遥测」承诺直接冲突**（🔴 第 4 章全部指标无采集手段）
2. **「记录时行情价折算」依赖的历史价格源不存在**（🔴 快照仅留 7 天，CSV 导入数月前的历史交易无法折算）
3. **备份恢复流程堵死了「新设备恢复」这个主要场景**（🔴 账户标识校验与故事 5.2 描述冲突）

## 四、本轮问题清单

> 严重度：🔴 必须解决｜🟡 应当解决｜🟢 建议优化

### 4.1 需求合理性 / 系统性问题

**🔴 N1. 成功指标与「无遥测」承诺直接冲突（L99、L162-171、L425）**
V1.2 新增了两处强承诺：「本产品不包含任何遥测、统计上报或第三方分析 SDK，所有网络请求仅用于行情数据与交易所 API」（L99）和关于页「不收集、不上传任何使用数据」（L425）。但第 4 章全部成功指标——激活率、WAU/MAU、API 同步使用率、资金记录使用率、多账户使用率、应用内 5 星评分占比、手动修正用户占比、CSV 导入成功率、API 首次连通率——**没有任何一个不依赖使用数据采集**。隐私承诺恰恰是本产品最大卖点，不可能为指标开遥测后门。
**建议（二选一，写进文档）：**
- ① 指标获取方式改为「无采集」模式：应用内提供本地统计面板（仅用户可见），指标通过用户主动导出诊断报告、社区问卷、内测样本人工回访获得，并在第 4 章注明每个指标的采集渠道与样本偏差；
- ② 增加「完全可选、默认关闭、匿名化」的 opt-in 统计（仅事件计数，无任何内容与标识），并同步修改 L99/L425 的表述。推荐 ①，与产品定位最自洽。

**🔴 N2. 「按记录时行情价折算」依赖的历史价格源不存在（L62、L216、L347、L863、L882）**
成本规范、增撤资折算、非 quote 手续费折算三处都规定「按记录时行情价/汇率折算」，但价格来源只有两条：行情 API 的**当前价**、price_snapshots 表（仅记录应用运行期间、保留 7 天）。以下高频场景全部无价格可用：
- CSV 导入数月前的历史交易（初始化主路径，故事 2.3），手续费折算和成本计算无法进行；
- 用户补录 30 天前的增资（base_amount 无法折算）；
- 用户间隔式使用，快照根本不覆盖记录时间。
**建议：** 明确规定折算价格的解析顺序，例如：① 本地快照命中（同日）→ ② 行情 API 历史价格接口（CoinGecko `/history`、CoinMarketCap historical 均支持）→ ③ 无网络时允许用户手填折算价，并在 UI 标注「历史价缺失，按当前价估算」的降级提示。该规则应写入全局说明「成本计算规范」一节。

**🔴 N3. 恢复流程堵死「新设备恢复」主场景（L288 vs L291、L411、L769）**
故事 5.2 描述的场景是「在新设备上或重装软件后恢复全部数据」，但验收标准 2 要求「校验备份文件内的账户标识与当前账户一致，不一致则提示并阻止恢复」——新设备/重装后根本不存在对应账户，按此规则永远无法恢复，故事描述与验收标准直接打架。另外流程上要求「先登录某账户再恢复」，新用户首次使用时没有可登录账户。
**建议：** 补一条恢复路径：启动向导或登录页提供「从备份恢复」入口，校验备份密码后**以备份内账户标识创建并恢复账户**；「恢复到已登录账户」保留标识一致性校验即可。两条路径都写进 5.2 与 9.9。

### 4.2 使用逻辑问题

**🟡 N4. 第 11 章正文版本残留（L899-901）**：标题已是「Out of Scope for v1.2」，正文仍写「排除在 **V1.0** 版本范围之外」。
**🟡 N5. 版本历史计数错误（L14）**：「完成 18 项修订」实际枚举了 ①～⑲ 共 19 条（更名那条未计入或计数笔误），改其一。
**🟡 N6. CSV 导入验收残留旧模型口径（L224）**：「正确更新持仓、**投入本金和资金余额**」——按新模型，交易不影响投入本金（只有增/撤资影响），「资金余额」概念也已废弃。应改为「正确更新持仓与持仓成本」。
**🟡 N7. 流程图 1 已有账户直接进仪表盘，跳过登录（L466）**：`B -- 是 --> J[跳转到仪表盘]` 绕过了密码验证，与流程图 7、严格模式安全模型矛盾。应改为「是 → 登录校验（或记住我会话恢复）→ 仪表盘」。
**🟡 N8. 交易管理页复制粘贴错误（L703）**：「列表显示**单币种**所有交易记录」系从 9.5 复制，应为「所有交易记录」。
**🟡 N9. 全量重放产生负持仓无处理规则（L65、L322、L736）**：余额不足阻止保存仅约束手动新增买入。以下路径均可导致重放后某币种持仓为负，文档无任何规则：① 编辑/删除一笔已被后续买入消耗的增资；② 删除一笔卖出；③ API 同步导入的交易与本地增撤资记录叠加。建议明确：重放校验失败时**阻止该次编辑/删除并提示冲突原因**；API 导入路径则允许负持仓并给出显眼的「持仓异常」标记（引导用户补录增资或校准）。
**🟡 N10. 持仓校准的产物未定义（L43、L267、L693）**：校准「生成一条记录并在同步日志留痕」，但该记录是什么类型（交易？资金流水？独立类型？）、是否影响投入本金与 ROI（应当不影响），全文未定义；数据模型中也没有校准记录表和同步日志表。若校准被当成撤资处理会直接污染 ROI，必须写死。
**🟡 N11. 数据模型与加密设计不闭环（L282-286 vs L846-853）**：5.1 设计了 DEK/KEK/KDF 分层架构，但 accounts 表只有 id/username/password_hash/created_at，**没有 KDF salt、KDF 参数、包裹后的 DEK（wrapped_dek）的存储字段**。另需补充：修改密码后，OS 钥匙串中基于旧 KEK 的会话令牌如何失效/更新。
**🟡 N12. 日志脱敏要求仍未加入（L365，上轮 S3 遗留）**：本地日志可导出分享，但未禁止记录 API 密钥明文/哈希、完整 API 响应体、金额与账户名。建议在第 6 章日志条目中补硬性脱敏要求。
**🟡 N13. 24h 盈亏的快照取值回退规则缺失（L41、L233、L882）**：快照每小时最多一条，而用户画像是「间隔式打开使用」，恰好 24 小时前有快照的概率很低。「无 24 小时前价格时显示 --」会导致该指标长期显示 --，失去意义。建议定义为「取距 24 小时前最近的快照（容差 ±6 小时），窗外才显示 --」；部分币种缺快照时是整体显示 -- 还是剔除该币种，也需明确。
**🟡 N14. 指标定义残留小问题（L163-164）**：WAU/MAU 的分母未定义（占累计注册用户？占安装量？）；「周/月留存率」的命名与其定义（周期内至少打开一次的活跃比例，即粘性）不符，建议改名「活跃率/粘性」或重定义为次周/次月留存。
**🟡 N15. 手续费自动计算公式未写死（L341、L739）**：费率 × 什么是未定义的。fee_currency 为 quote 时 fee = rate × 总价；为 base 时 fee = rate × 数量——应明确，否则各交易所规则实现会分叉。
**🟡 N16. 编辑历史记录与「撤资持仓不足」规则的连锁冲突（L314、L322）**：撤资保存时校验持仓不足，但编辑一笔历史增资调小金额后，其后的撤资在重放中可能不再满足校验。阻止还是放行，未定义（可与 N9 合并为统一的「重放校验规则」）。
