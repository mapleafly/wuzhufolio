# 桌面端 PRD 法币方案决策分析

**背景:** 《桌面端prd评审报告V3》T4 指出：法币↔法币汇率无数据源（CoinGecko / Binance 均不提供）。产品负责人提出方向：**账本内是否还需要“法币”这个资产概念？增资/撤资全部使用稳定币，法币只在计算展示（盈亏、资产、成本）时作为计价单位。** 本文分析该方向的可行性、对 PRD 的影响，并给出备选方案。
**日期:** 2026-08-26
**状态:** 已决策并落地（见文末 H 节决策记录；对应修订已写入《桌面端prd.md》V1.4）

---

## A. 概念澄清：法币在产品中承担了三个角色

| 角色 | 含义 | 现状 PRD（V1.3） | 用户提议 |
| --- | --- | --- | --- |
| 计价单位 | 净值/盈亏/成本/投入本金的展示维度（基础法币，L40、L424） | 保留 | **保留（唯一保留）** |
| 账本资产 | 以法币代码入账的持仓（增资 USD/CNY 形成“USD 持仓”，L33-35、L887） | 存在 | **取消** |
| 入金媒介 | 用户真实世界的钱（银行→交易所，通常先兑换为稳定币） | 与账本资产混同 | 显式剥离：记录兑换后实际到账的稳定币 |

现状 PRD 把“计价单位”与“账本资产”混在一个“币种不限（法币、稳定币或其他加密货币均可）”（L32-35）里，T4 正是这个混淆的代价。

## B. 现状比 T4 更严重：法币持仓分支是“三重断裂”

1. **折算无源**（T4 原发现）：增资 USD、基础法币 CNY 时，base_amount 需要 USD/CNY 汇率；CoinGecko 只提供“币种→多法币”报价，无法币→法币端点（L85、L424 规定汇率来自行情 API 多法币报价）。
2. **快照表无法表达**：price_snapshots 的行是 (symbol, fiat, price)（L899-907），数据来源是行情 API 多法币报价（L249）——一条“USD 对 CNY”的价格行**没有生产者**。快照表结构上就容不下法币资产。
3. **24h 回溯无源**：24h 盈亏需要“24 小时前价格”（L42），回填走 market_chart（币种维度），对法币持仓无从回填。

**结论：法币作为账本资产，在现有数据源体系内本就不可实现。这不是“要不要删”的偏好题，而是“必须改”的修复题**——下面三个备选方案只是改法不同。

## C. 用户方向（稳定币账本 + 法币计价）可行性论证

**C.1 可行，且与现有默认路径天然一致。** L222 已规定增资默认“基础法币 USD→USDT、其余→USDC”：文档的主路径本来就是稳定币入账，法币入账是例外分支。提议只是把默认路径扶正为唯一路径。

**C.2 数据源完全闭合。** 账本内全部资产（加密货币 + 稳定币）都是 CoinGecko 可定价币种；基础法币退化为纯报价维度（vs_currencies）。这正是 CoinGecko 自身的数据模型（资产 = 币，法币 = 报价维度），方案与数据源天性契合。切换基础法币变成纯重标价，无任何转换残留。

**C.3 保真度与现状等价（关键论证）。** 质疑者会问：“我充 35,000 CNY 买到 5,000 USDT，OTC 有溢价，稳定币入账会不会失真？”答案：**现状模型同样捕捉不到溢价**——V1.3 规定“记录时行情价一律 API 回填、不支持用户手填价格”（L87），无论入账币种是 CNY 还是 USDT，折算都按市场价。OTC 实付金额在两种模型下都不可表达，差异为零。真正有差异的只有一处：“交易所法币余额”（Coinbase 的 USD 余额、Binance 的 EUR 钱包）——现状模型名义上可跟踪（实际因三重断裂不可用），稳定币模型明确不入账（可近似记录为对应稳定币）。

**C.4 附带收益。** ① 24h 盈亏不再混入法币汇率波动（更纯粹反映资产价格变动，脱锚事件仍会如实计入，这是正确行为）；② V3 T9（币种主数据）简化，无需 ISO 4217 识别分支；③ 快照表语义闭合；④ “现金类币种”收窄为稳定币白名单，一处收口；⑤ 中文用户不受影响——CNY 作为基础法币的全部计价展示能力原样保留，被取消的只是“以 CNY 代码入账的人民币持仓”这一本就不可实现的分支。

**C.5 唯一真实损失。** 交易所法币余额不入账。需在 Out of Scope 显式声明，并给出近似做法（按 1:1 记录为对应稳定币，误差 = 脱锚幅度，通常 <0.3%）。

## D. 落地要补的三条规则（不是删概念就完事）

1. **表单与文案**：增资/撤资币种选择器限定为加密货币/稳定币；用户输入法币代码（USD/CNY）时提示“法币入金请记录兑换后实际到账的稳定币数量”。（可选增强：法币金额辅助输入——用户输 35,000 CNY，按当前 USDT/CNY 报价折算出 USDT 数量预填，确认后入账。）
2. **法币计价交易对的归一化**：Coinbase 的 BTC/USD、Binance 欧洲区的 BTC/EUR 等交易对经 API/CSV 导入时，quote 腿需要落点。规则：按“法币→稳定币孪生映射表”1:1 映射（USD→USDT/USDC、EUR→EURC，映射表可配置，与增资默认映射共用一张表以保证账本守恒）；无孪生映射时按“第三币种手续费”语义处理（仅计入基础币种持仓与成本，不联动 quote 持仓）。**联动决策：V3 T14 建议 MVP 交易所收敛为 Binance（交易对基本为稳定币/币币计价），若采纳，本规则可推迟到 Coinbase 接入时再定。**
3. **交易所法币余额**：API 同步只导入交易、校准为手动逐币触发，法币余额默认不进入账本；Out of Scope 声明 + 近似做法说明（见 C.5）。

## E. 备选方案对比

| 维度 | 方案 0：维持现状 | 方案 A：纯稳定币账本（用户方向） | 方案 B：保留法币资产 + 稳定币桥 | 方案 C：新增法币汇率源 |
| --- | --- | --- | --- | --- |
| 做法 | 保持“币种不限（法币…）” | 法币仅计价；增撤资 = 稳定币/加密货币 | 法币仍可入账，价格 = 参考稳定币双法币报价之比：FX(A→B) = price(USDC,B) ÷ price(USDC,A) | 接入第三方法币汇率 API（如基于欧央行牌价的免费档） |
| T4 三重断裂 | ❌ 全部保持断裂 | ✅ 彻底消除 | ✅ 消除（价格含脱锚误差） | ✅ 消除（价格精确） |
| 法币余额保真 | 名义支持、实际不可用 | ❌ 不入账（可 1:1 近似） | ✅ 跟踪 | ✅ 跟踪 |
| 新增依赖 | 无 | 无 | 无 | +1 数据源（额度/可用性/失败模式 +1） |
| 规则复杂度 | 低（但规格不自洽） | 低（+1 条归一化规则） | 高：折算/快照/24h/白名单四处都要加“法币走桥接”分支 | 中：新数据源章节 + 缓存 + 降级策略 |
| 隐私承诺影响 | 无 | 无 | 无 | 需修订 L111“所有网络请求仅用于行情数据与交易所 API” |
| 改动量 | 0 | 小（见 F 节清单） | 中 | 中-大 |
| 适合场景 | — | **MVP（推荐）** | 后续版本若法币余额需求强烈 | 若要求法币余额精确计价 |

**推荐方案 A。** 理由：① 这是修复三重断裂的唯一“减法”方案；② 与既有默认路径（L222）、既有 MVP 风格（“简化口径 + 显式声明局限”，如 ROI 资金加权、90 天前日线精度）一脉相承；③ 唯一损失是边缘场景且有 1:1 近似路径；④ 方案 B 的全部保真收益只为“交易所法币余额”服务，却要在四套规则里引入桥接概念；⑤ 方案 C 违反现有网络白名单承诺。**后续版本若法币余额需求强烈，可从 A 平滑升级到 B：账本结构不变，只增加定价规则，无迁移成本。**

## F. 方案 A 的 PRD 改动清单（精确到条目）

1. **名词解释**：L33 可用现金余额删去“法币（按 ISO 4217 代码识别）+”；L34/L35 增资/撤资币种范围改为“稳定币或其他加密货币”+ 法币入金提示；L40 基础法币角色改为“仅作计价与展示单位”；新增“法币→稳定币孪生映射表”词条。
2. **全局说明**：新增小节“法币角色与归一化规则”（D 节三条）；L86-89 行情规则补一句“账本内全部资产均为行情源可定价的币种”。
3. **用户故事**：2.2 验收 2（L222）、6.1/6.2 验收（L313、L321）、9.8 表单（L777）同步收窄币种范围；2.3/4.1 的 CSV/API 验收补“法币计价交易对归一化”条目（或随 T14 收敛交易所而推迟）。
4. **数据模型**：capital_flows.currency 描述（L887）由“任意币种，如 USD、CNY、USDT、BTC”改为“加密货币或稳定币（如 USDT、BTC）”；无 schema 破坏性变更（currency 为自由文本，域收窄不需迁移）；（可选）settings 增加“法币→稳定币映射”键。
5. **Out of Scope（第 11 章）**：新增“法币现金与交易所法币余额的直接入账（法币仅作计价单位；法币入金请记录兑换后的稳定币到账；后续版本可评估法币资产支持）”。
6. **评审联动**：V3 的 T4 关闭、T9 简化；T3（跨端同步）清单 +1 项（移动端名词解释 / 故事 2.2、6.1、6.2 / 数据模型 / Out of Scope 需同步修订）。
7. **（可选增强，随 A 一并决策）**：法币金额辅助输入（D 节第 1 条）；OTC 实付注记字段（增资表单可选“实际支付法币金额”，仅展示与审计用、不参与计算——弥补 C.3 所述“溢价不可表达”的遗憾，为将来升级 B/C 留数据）。
