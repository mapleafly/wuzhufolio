# 桌面端 PRD 三大方向决策分析

**背景:** 针对《桌面端prd评审报告V2》的三个 🔴 问题（N1 成功指标 vs 无遥测、N2 历史价格源、N3 备份恢复路径），产品负责人给出了方向性意见。本文分析其可行性、调研支撑事实、对 PRD 的影响，并列出需决策项。
**日期:** 2026-08-26
**状态:** 已决策并落地（见文末决策记录；对应修订已全部写入《桌面端prd.md》V1.3）

## A. 成功指标与开源/闭源

### A.1 用户方向可行性

**取消应用内采集指标、改用外部指标（下载量、星数）——完全可行，且这是与「无遥测」承诺唯一自洽的方案。** 外部指标不需要应用内任何数据采集，L99 和 L425 的隐私承诺原封不动即可成立。

不同指标的来源渠道：

| 指标 | 采集方式 | 前提 |
| --- | --- | --- |
| 下载量 | 发布渠道统计（GitHub Releases 下载计数、官网下载日志、Microsoft Store / 第三方商店后台） | 无 |
| GitHub 星数、Fork、Issue 活跃度 | GitHub 公开数据 | 需开源 |
| 社区评价（Reddit/V2EX/推特） | 人工观察 | 无 |
| 核心功能可用性（原「过程指标」） | 内测期招募 20–50 名种子用户，自愿导出匿名诊断报告 + 问卷 | 无 |

原第 4 章的激活率、WAU/MAU、功能使用率、应用内评分、手动修正占比等指标**全部删除或转化**（过程指标转为内测期人工统计），文档明确「MVP 阶段不设遥测类指标」。

### A.2 开源 vs 闭源分析

| 维度 | 开源 | 闭源 |
| --- | --- | --- |
| **隐私卖点可验证性** | ✅ 「无遥测、本地加密」可被任何人审计验证——对以隐私为核心卖点的产品，这是**决定性优势** | ❌ 承诺只能靠信任，与云端工具的差异无法自证 |
| **目标用户匹配** | ✅ 画像 Alex 是技术型用户，会看源码、会自己构建；开源直接提升转化 | ⚪ 无加成 |
| **指标获取** | ✅ 星数/Fork/Release 下载/Issue 全是现成公开指标 | ⚠️ 只剩下载量（需自建下载渠道统计） |
| **商业化路径** | ✅ 有成熟先例：Rotki（AGPL-3.0，本地优先，Premium 订阅解锁高级功能）、Ghostfolio（AGPL-3.0，官方托管收费）——两者均是与本产品同品类的组合追踪工具 | ✅ 直接付费授权，但小众隐私工具闭源付费转化率存疑 |
| **风险** | ⚠️ 可被 Fork 换皮；AGPL 可阻止他人闭源商用（含 SaaS 托管） | ⚠️ 需自行建立信任（代码审计报告等成本高） |
| **安全** | ✅ 加密实现公开可审计是加分项（密码学「公开算法、保密密钥」原则） | ⚪ — |

来源：[Rotki LICENSE](https://raw.githubusercontent.com/rotki/rotki/develop/LICENSE.md)、[Ghostfolio LICENSE](https://raw.githubusercontent.com/ghostfolio/ghostfolio/main/LICENSE)（均为 AGPL-3.0，已核实）。

### A.3 建议

**建议开源，许可证 AGPL-3.0。** 理由：① 隐私是本产品第一卖点，可验证性 > 保密性；② 同品类两个最直接先例（Rotki、Ghostfolio）都是 AGPL 开源 + 增值收费，商业路径已被验证；③ 指标问题自然解决。**即使暂不定开源与否，第 4 章也应先按「仅外部指标」重写**——两种路线都兼容，不阻塞。

> **决策项 D1：** 开源（AGPL-3.0，推荐）／ 闭源 ／ 暂不定，第 4 章先按外部指标重写

## B. 行情数据 API 能力与「数据决定结构」分析

### B.1 调研事实：各平台免费档能提供什么（2025–2026 核实）

| 平台 | 当前价 | 历史价格 | 粒度 × 跨度 | 限额 | 多法币 |
| --- | --- | --- | --- | --- | --- |
| **CoinGecko**（免费 Demo 档） | ✅ `/simple/price`（一次多币×多法币）、`/coins/markets` | ✅ `/market_chart`、`/market_chart/range`、`/coins/{id}/history` | ≤1 天：5 分钟；**2–90 天：小时线**；**>90 天：日线**；显式 `hourly` 最多回溯 100 天；`days=max` 可取上市至今全部日线 | **30 次/分钟，10,000 次/月** | ✅ `vs_currencies=usd,eur,cny,...` |
| **CoinMarketCap**（免费 Basic 档） | ✅ quotes/latest | ❌ **历史端点需付费**（Hobbyist 起，3 年；全量需更贵档） | — | 15,000 credits/月 | ✅ |
| **Binance 公共 API**（无需 key） | ✅ | ✅ `/klines` 分页可回溯至该交易对上市之初 | 1m–1M 任选，单次最多 1000 根 | 按权重限速，免费 | ⚠️ 仅交易所交易对（USDT 等计价），非法币 |
| CoinCap / CryptoCompare | ✅ | ✅ 有限 | 小时/日线 | 额度不透明或偏低 | 部分 |

来源：[CoinGecko market_chart 官方文档](https://docs.coingecko.com/reference/coins-id-market-chart.md)、[market_chart/range](https://docs.coingecko.com/reference/coins-id-market-chart-range.md)、[simple/price](https://docs.coingecko.com/reference/simple-price.md)、[CMC OHLCV 历史数据说明](https://coinmarketcap.com/academy/article/the-ohlcv-backfill-playbook-how-to-pull-historical-crypto-data-without-wasting-calls)、[Binance K线端点](https://developers.binance.com/docs/binance-spot-api-docs/rest-api/market-data-endpoints)。

### B.2 直接回答：能否一次获取覆盖全时间域的数据？

**日线级：能。** CoinGecko `market_chart?days=max` 或 `market_chart/range` 一次（长区间分页）即可拿到某币种上市以来的全部日线，多法币。
**小时级：不能全量。** 免费档小时线最多回溯约 90–100 天；更早只有日线。5 分钟级仅限近 10 天且需付费档。
**结论：产品的时间分辨率边界是「近 90 天小时级、90 天以前日级」，这必须上升为全局数据规则写进 PRD。**

⚠️ 一个待验证点：CoinGecko 文档注明**付费 Basic 档**历史限最近 2 年，免费 Demo 档 `days=max` 是否同样受限未在文档中明示，开发期需用真实 key 实测；若受限，超长历史日线可用 Binance K线兜底（上架币）或接受边界声明。

### B.3 主数据源建议

**主源：CoinGecko 免费 Demo 档**（当前价 + 多法币 + 历史回填三需求唯一免费全覆盖；个人/家庭级使用 1 万次/月足够）。**兜底/校验：Binance 公共 K线**（免费无限额、分钟级、全历史，但仅 Binance 在架交易对）。**CMC 免费档不能做历史回填，不建议作为主源**（可在「关于」中列为后续付费升级选项）。

### B.4 对 PRD 数据结构、边界、规则的影响（「数据决定结构」落地清单）

1. **快照保留：7 天 → 永久保存（带降采样）。** 用户的判断正确，7 天不合理。建议规则：近 90 天保留小时级快照，更早的自动压缩为日级快照（每日 00:00 UTC 一条）；仅对「账户持仓涉及币种 + 现金类币种 + 使用中的法币」写快照。体积估算：30 个币 × 3 法币 × (2160 小时 + 275 日线)/年 ≈ 22 万行/年，SQLite 下仅数 MB，永久保存无压力。
2. **24h 盈亏规则重写（解决 V2 的 N13）：** 不再依赖「本地恰好有 24h 前快照」——取数顺序：本地快照命中 → 未命中则调用 `market_chart`（90 天内小时级）回填 → 仍无（>90 天无小时级/新币/API 无数据）显示「--」。「间隔式使用」不再导致该指标长期失效。
3. **历史折算规则（解决 N2，取消手填）：** 所有「记录时行情价」一律从 API 回填：≤90 天取当日小时线（取记录时刻所在小时），>90 天取当日日线（00:00 UTC 快照），并在全局说明中声明「90 天以前的记录按当日日线价折算，存在日内误差」的 MVP 精度局限。
4. **离线场景的替代设计（不手填价格的前提下）：** 联网是折算前提。离线保存历史记录时提供两个方案：
   - **方案 a（推荐）：「待定价」状态**——允许保存，记录标记 `price_status = PENDING`，指标暂按最近可得价估算并标注「估算中」；联网后自动回填真实价并重算持仓成本与指标。体验好，实现复杂度可控。
   - **方案 b：阻止保存**——提示「折算需要联网获取历史价格」。简单但打断初始化主流程（CSV 导入尤其常见）。
   > **决策项 D2：** 离线历史记录按方案 a（待定价+自动补算，推荐）／方案 b（阻止保存）
5. **新增后台任务规则：** 「历史价格回填任务」——对 PENDING 记录、初始化导入、快照空洞进行按需回填，受 CoinGecko 月度额度约束需做批量合并（`/market_chart/range` 一次取区间）与去重。
6. **数据结构随之调整（待决策后落 PRD）：** `price_snapshots` 保留策略改永久+降采样；`transactions`/`capital_flows` 增加 `price_status`（OK/PENDING）与 `price_source` 字段；名词解释增加「时间分辨率规则」。
7. **功能边界确认：** 该数据能力对 MVP 全部功能（仪表盘、24h 盈亏、成本、ROI、饼图）构成充分支撑；未来版本加「净值历史曲线图」时数据源已天然具备，可在 Out of Scope 中注明「已预留数据基础」。

## C. 备份恢复方案

### C.1 用户方案确认与收益

**备份不含账户信息、可在新软件/新账户/未来移动端导入——该方案成立，且是比评审报告 V2 更优的解：** V2 建议的「备份内嵌账户标识 + 恢复时校验一致」是为了防误恢复，但它堵死了新设备迁移主场景（N3）。去掉账户标识后 N3 自然消解，跨平台兼容性也天然获得。V2 的其余备份建议（密码验证、二次确认、进度提示、E3 备份摘要）全部保留且不冲突。

### C.2 备份内容清单（按用户方向具体化）

| 包含 | 说明 |
| --- | --- |
| transactions、capital_flows | 含 source、exchange_order_id |
| fee_rules、settings（账户级）、api_keys | api_keys 属高敏数据，导出前需显著提示「备份文件包含 API 密钥」 |
| reconciliation_records | 校准留痕 |
| **price_snapshots** | 仅限本账户涉及币种与相关法币，且按降采样策略（近 90 天小时级 + 更早日级）；理由：快照数据可随时从 API 重新获取，全量打包徒增体积——30 币 × 3 法币降采样后约数万行、几 MB，自包含与体积取得平衡 |
| **不包含** | accounts 表任何字段（用户名、密码哈希、KDF 参数、wrapped_dek）；全局设置 |

文件结构建议：明文头部（格式版本、应用版本、导出时间、各表记录条数、时间范围——供恢复前摘要展示，即上轮 E3）+ 加密载荷（AES-256-GCM，JSON 格式 payload 而非裸 SQLite 文件，保证未来移动端/跨版本可读）。

### C.3 加密与密码语义

备份密码是**文件的密码，与账户脱钩**：导出时由用户设置（界面默认填入当前账户密码，可修改）；任何设备上导入都只需该文件密码。PRD 中「恢复时输入备份时对应的账户密码」的表述需改为「输入备份文件密码」。

### C.4 全量 vs 增量导入

这是本方案唯一需要先补一个数据模型改动的地方：**当前各表主键为自增 Integer，跨设备/跨安装必然撞号，增量合并无从谈起。** 需为 `transactions`、`capital_flows`、`reconciliation_records` 增加 `uuid` 字段（记录创建时生成，自增主键保留作本地排序用）。

- **增量合并（推荐默认）：** 去重优先级：uuid 精确匹配（跨设备同一记录）→ exchange + exchange_order_id（API/CSV 记录）→ 模糊匹配提示（无 ID 的手动记录）；price_snapshots 按 (symbol, fiat, recorded_at) 天然幂等合并。优点：可重复导入同一文件无副作用、适合「桌面 + 未来移动端」双向补数据。
- **全量覆盖（显式选项）：** 二次确认 + 覆盖前自动先为当前数据生成一个临时备份（防呆）。
> **决策项 D3：** 默认增量合并 + 全量覆盖为显式选项（推荐）／ MVP 只做全量覆盖（实现最简，但移动端时代必然要补增量）

### C.5 遗留小问题

- 用户提到「增资撤资转账记录」——当前模型无独立「转账」类型，外部转入/转出已归入增资/撤资（站内划转在 Out of Scope），备份范围按现有类型覆盖即可，无需改动。
- 增量合并若合并了记录，需触发全量重放重算（复用成本规范的既有规则）。
