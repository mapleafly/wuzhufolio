## 一、评审结论摘要

**总体判断：文档自身维度已接近可冻结基线——V2 的三个 🔴（指标 vs 无遥测、历史价格源、备份路径）通过“先调研、再决策、后修订”的方式高质量闭环，27 项遗留中 23 项完全解决、上轮 🟢 建议首次全清。但当评审半径从“这份文档”扩大到“这个产品”（跨文档、工程可行性、发布运营）后，暴露出 3 个新的 🔴 系统性问题：校准机制的账务语义不完整（会产生错误数据）、行情免费额度在默认配置下不可持续（产品会在月中失去行情）、桌面与移动两份 PRD 已实质分叉（桌面端 V1.3 的跨端导入验收标准在现有文档体系下无法成立）。建议完成 T1-T3 及高优 🟡 后冻结 V1.4 基线。**

亮点（本轮新增）：

- **修订方法论升级**：三大决策问题不是打补丁解决，而是先做数据源能力调研（CoinGecko 免费档粒度/额度、Binance K 线全历史，附来源链接）再定结构——“数据决定结构”的顺序正确，且留下 D1-D5 决策记录可供追溯。这套流程值得固化为团队惯例。
- **“待定价”机制设计优雅**（L43、L88）：离线允许保存 + PENDING 标记 + 联网自动回填重算，既守住了“价格一律来自行情源、不支持手填”的数据纪律，又不打断初始化主流程。
- **备份方案比 V2 建议更彻底**：不含账户信息 + 独立备份文件密码 + 增量合并默认（uuid / 订单号 / 模糊三级去重）+ 明文头部摘要 + 全量覆盖自动临时备份，一次性打开新设备、跨账户、未来移动端三个场景，防呆设计完整。
- **上轮全部 🟢 建议项一次性纳入**（E1 行内编辑 L726、E3 恢复摘要 L302/L570、E6 导入影响摘要 L229、E7 流程图 2 简化 L494-496），三轮以来首次 🟢 全清，文档收敛态度积极。
- **指标体系与无遥测承诺完全自洽**，且对开源/闭源两条路线兼容（L175），“暂不定开源”不阻塞指标口径，分寸得当。

本轮系统性问题（按严重度，详见第四节）：

1. **🔴 T1 校准机制的账务语义存在三处缺口**：比对基准未定义（多交易所/含手动记录时校准会错误削减持仓）；推导链不含校准记录（任何后续编辑触发重放会静默回滚校准结果）；负差额按市价移出成本与“不产生盈亏”自相矛盾。
2. **🔴 T2 行情额度预算在默认配置下被击穿**：托盘常驻 + 5 分钟刷新 ≈ 8,640 次/月，叠加回填已贴着 CoinGecko 免费档 10,000 次/月上限；1 分钟档 43,200 次/月超限 4.3 倍；且 6.1 与 9.2 对托盘期间行情刷新频率的表述互相矛盾，429 退避与兜底切换规则缺失。
3. **🔴 T3 跨端文档分叉**：桌面 V1.3 的核心决策（备份格式、快照永久+降采样、行情源、无遥测指标、待定价机制等）全部未同步到移动端 V1.1；两份文档对 .cpro 的定义直接冲突，桌面端“支持未来移动端导入”的验收标准失去支撑。

## 四、本轮问题清单

> 严重度：🔴 必须解决｜🟡 应当解决｜🟢 建议优化

### 4.1 系统性问题（新引入 / 深挖）

**🔴 T1. 持仓校准的账务语义不完整（三处缺口，V1.3 新增机制的推演欠账）**
引用：L45（名词解释）、L63（平均成本按账户合并、不分交易所）、L275（故事 4.1 验收 5）、L67-69（重放规则）、L895（持仓推导链）、L922-935（reconciliation_records）。

- **① 比对基准未定义。** 本地持仓是跨交易所合并计算的，而校准是“用交易所 API 返回的余额修正本地持仓数量”（L45）。用户在 Binance 和 Coinbase 各有 1 BTC（或另有手动记录）时，本地持仓 2 BTC，“校准”按钮使用哪一家 API 的余额？若按现文直接把合并持仓“修正”为单家交易所的余额 1 BTC，将**静默吞掉另一家交易所的资产**。必须定义：校准仅适用于“该币种仅关联单一 API 且无手动/CSV 记录”的场景，或改为“按来源分账本校准、本地其他来源数量保持不变”。
- **② 与全量重放/推导链脱节。** L895 规定“全部币种持仓由 transactions 与 capital_flows 统一推导”，重放规则（L67-69）同样只枚举交易与资金记录。那么校准的效果存放在哪里？若校准不入推导链，**任何一次后续的新增/编辑/删除/导入触发的重放都会静默回滚校准结果**（用户刚校准完，编辑一笔旧交易，持仓又变回错误值）；若入链，校准作为绝对锚点与“负持仓校验”的先后交互也未定义。建议：校准记录按时间戳作为推导序列的第三类事件参与重放（锚点语义：该时刻起持仓 = 交易所余额），并写进“成本计算规范”。
- **③ 负差额规则自相矛盾。** “差额数量按校准时市价计入/移出持仓成本”（L275、L935）与“不产生盈亏、不影响 ROI”（L935）冲突：设市价 p、平均成本 c，若 p ≠ c，按 p 移出 |delta| 个单位的成本会隐含确认 |delta|×(p−c) 的已实现盈亏并改变剩余持仓的平均成本。应改为**非对称规则**：正差额按校准时市价计入成本（同增资语义）；负差额按当时平均成本移出（同撤资语义）。

> **【2026-08-26 更新】** 经产品负责人确认（方案甲 + 四点规则），V1.7 落地：①适用条件限定为单一数据来源币种（多来源隐藏入口并提示改用补录/增撤资）；②校准记录按时间戳作为推导序列第三类事件（锚点语义）参与全量重放，历史记录编辑不再回滚校准效果，负持仓校验按锚点前后分段执行；③非对称成本规则（正差额按校准时市价、负差额按当时平均成本）；④差额视同系统生成的资金操作计入累计增资/撤资（恒等式“总收益=净值+撤资−增资”保持成立、零凭空盈亏；正差额增大 ROI 分母，保守口径），推翻 V1.3“不影响投入本金与 ROI”表述；⑤reconciliation_records 补 exchange、base_amount 字段，校准记录以“校准”类型进入资金管理列表与币种详情页校准历史。本项关闭。

**🔴 T2. 行情额度预算：默认配置即可击穿免费档（含托盘策略自相矛盾）**
引用：L247、L429（6.1）、L451（9.2）、L681/L695（刷新频率）、L89（回填批量合并）；三大决策分析 B.1（CoinGecko 免费档 30 次/分钟、10,000 次/月）。

- **算术**：/simple/price 单次可批量全部币种 × 多法币，即一次刷新 = 1 次调用。默认 5 分钟刷新：12 次/时 × 24h × 30 天 = **8,640 次/月**；叠加 24h 前价格回填（快照未命中时每币种 1 次 /market_chart，且该接口不可跨币种合并，30 个币种一次缺档就是 30 次调用）、初始化/补录的区间回填、切换法币后的新快照——默认配置已贴着 10,000 次/月上限。1 分钟档 = **43,200 次/月，超限 4.3 倍**。而 9.1 规定关闭窗口默认驻留托盘、9.2 规定托盘期间持续刷新，等于“开机即消耗”。决策分析 B.1 判断“个人/家庭级 1 万次/月足够”时并未做这笔算术。
- **自相矛盾**：6.1（L429）说行情刷新与 API 同步是“两个相互独立的定时任务，分别按各自频率执行”，9.2（L451）却说托盘驻留期间“按设置中的同步间隔自动执行 API 同步与行情刷新”——两处对托盘期间行情刷新频率的表述冲突，两种读法分别导致“24/7 刷新（额度必爆）”与“托盘降频（与 6.1 矛盾）”。
- **缺失规则**：429 指数退避、月度额度看板/预算、“额度耗尽”的错误分类与用户提示（目前仅覆盖网络断开/密钥失效）；Binance 作为“兜底与校验源”（L246）的触发条件未定义（请求失败？429 限额？币种未收录？），主备切换是无感还是有提示也未说明。Binance 公共 K 线免费且按权重限速，完全可以作为额度耗尽后的当前价兜底。

> **【2026-08-26 更新（V1.5/V1.6）】** V1.5 已定义兜底切换规则（触发条件、折算链、UI 标注、自动回落、24h 同源原则）；V1.6 按产品负责人方向将兜底源由 Binance 公共 K 线改为 **CoinMarketCap 免费档**（理由：①Binance 兜底在 CG 故障时“K线×USDT/法币”折算链断裂（法币腿仍需 CG）；②CMC quotes/latest 经 convert 直出多法币（含 CNY）、批量当前价、无链式换算；③兜底需用户自配 CMC Key，避免开源内置共享 Key 的集体限流与滥用风险）。**额度治理已落地**：行情刷新频率改为 5/15/30 分钟（默认 5，移除 1 分钟档）、托盘驻留期间统一按 API 同步间隔降频（6.1 与 9.2 表述冲突消除）、窗口恢复立即刷新、月度调用计数 + 80% 自动降档 + 429 指数退避；新增流程图 9“行情数据刷新流程”。V1.7 补充 Key 政策：CoinGecko 与 CoinMarketCap 均不使用内置共享 Key，统一由用户在设置中配置个人 Key（CoinGecko 必填启用行情功能，CoinMarketCap 可选启用兜底）。V1.8 再优化为两级模式：CoinGecko 默认使用无 Key 公共 API 开箱即用（按 IP 共享限流），配置个人 Key 后自动切换专属额度并启用额度治理（CG Key 由必填改为可选）；CoinMarketCap 无 Keyless 模式、兜底仍需个人 Key。本项关闭。

**🟡 T4. 法币↔法币汇率无数据源**

### 4.7 产品打磨与战略

**🟢 T16. 打磨包（数据主权与数据韧性）**
① 定期备份提醒（可选开关）——“忘记密码 = 数据全失”的产品里，备份提醒是最高价值的安全网；② 备份密码强度校验（同账户密码标准，见 T6）；③ 诊断报告内容规范（L178 引用但未定义，应复用日志脱敏规则并列举字段）；④ 微小价格币种的精度自适应（L60 固定 8 位小数，部分 meme 币单价有效数字不足 8 位会显示为 0）；⑤ sync_logs 与本地日志的轮转/上限策略；⑥ 输入 API 密钥后的剪贴板清理提示（剪贴板历史云同步是真实泄露面）；⑦ **明文数据导出（CSV/JSON）**——“数据主权”承诺应包含“离开的自由”，目前唯一的出口是加密 .cpro，用户无法把数据带走迁移到任何其他工具。

> **【2026-08-26 更新】** V1.9 落地：①备份提醒设置项（默认开启、30 天阈值）；②备份密码强度（随 T6）；③诊断报告内容规范（日志章，复用脱敏规则并列举字段）；④微小价格币种精度自适应（数据精度规则）；⑤日志与 sync_logs 轮转上限（各 1 万条/90 天）；⑥保存 API 密钥后剪贴板清理提示（9.10）；⑦明文 CSV 导出（9.9，不含 API 密钥；JSON 导出延后）。本项关闭。

## 六、三轮评审演进小结

| 轮次 | 评审对象 | 方法 | 主要发现层次 |

三轮的 🔴 逐步从“文档写错了”（R1）→“修订改出的冲突”（R2）→“文档没写到的地方”（R3），符合文档成熟度曲线。当前文档在“写了的部分”质量已高，剩余风险集中在**跨文档治理**与**工程选型**两处——它们已超出单份 PRD 的传统边界，需要的不是更多文字校对，而是把共享规范、架构决策、发布计划显式纳入产品文档体系。
