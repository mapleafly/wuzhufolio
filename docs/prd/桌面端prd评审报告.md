## 一、评审结论摘要

**总体判断：方向正确，定位清晰，但当前版本还不能直接作为开发基线，需要 1～2 轮修订。**

亮点：

- 「数据完全本地化 + 隐私优先」的差异化定位清晰，与竞品（云端组合跟踪工具）的对比鲜明，价值主张 6 条（第 1 章）基本自洽。
- 多账户隔离、增资/撤资资金流水、投入本金与 ROI 的概念体系是真实痛点（第 2 章问题陈述能站得住）。
- 交互细节考虑得比较细：空态占位、缺省值“--”、默认排序、实时计算总价/手续费、红绿盈亏、深浅主题、I18N 等都有覆盖。

硬伤（按严重度排序，详见后文）：

1. **ROI 计算公式在“撤资”场景下会产生错误结果**（🔴 数学错误，直接误导用户）
2. **“可用现金余额”模型不闭合**（🔴 法币现金与币币交易之间没有更新规则）
3. **24 小时盈亏需要历史价格快照，但数据模型里没有**（🔴 无法实现）
4. **“切换账户无需密码”与“无密码无法解密”互相矛盾**（🔴 安全体系自相矛盾）
5. **API 同步与手动/CSV 数据无合并与去重规则**（🔴 会产生重复记录或余额被覆盖）
6. **文档版本状态混乱**：V1.0 与 V1.1 在副标题、编号、版本历史、目录、第 5 章标题五处不一致（🔴 评审基线不清）

## 三、问题清单

> 严重度：🔴 必须解决（否则开发无法正确进行或会产生错误数据）｜🟡 应当解决（影响体验、安全或可维护性）｜🟢 建议优化（加分项）

### 3.1 需求合理性问题

**🔴 R1. ROI 公式在撤资场景下数学上错误（L34-35、L285-288）**
现行定义：投入本金 = 增资 − 撤资；ROI =（当前资产净值 − 投入本金）÷ 投入本金 × 100%。
反例：用户增资 100，盈利后卖出并撤资 150，此时投入本金 = −50，资产净值 = 0，ROI =（0−(−50)）÷(−50) = **−100%**，而实际收益是 +50%。只要“撤资 > 增资”（盈利后提现，正是最常见场景），分母即为负数或接近 0，结果完全失真；投入本金 = 0 时还会除零。
**建议：** 改用资金加权口径：总收益 = 当前资产净值 + 累计撤资 − 累计增资；收益率 = 总收益 ÷ 累计净增资（分母做 ≤0 保护）。同时明确该口径不含时间加权（MVP 可接受，但要写进文档说明局限）。

**🔴 R2. “可用现金余额”模型不闭合（L31、L199、L270-271、L279-280）**
名词解释定义现金余额是“法币金额”；但交易对是 BTC/USDT 这类币币交易，全篇没有任何规则说明：买入 BTC/USDT 是否会扣减法币现金、卖出是否增加、汇率从哪来。结果是增资/撤资只改现金，交易只改持仓，两条账永远对不上；且 USDT 等稳定币既是“持仓”又近似“现金”，可能与法币现金重复计价。
**建议：** 二选一并写死规则：① 现金余额按币种记账（如 USD/USDT 分账户），买入时按“计价币种”扣减对应现金；② 或干脆弱化“现金余额”为“累计净投入展示值”，不参与交易联动。法币换算需要明确汇率数据源。

**🔴 R3. 24 小时盈亏无法实现且口径混入资金流（L200-201、L345、L600、L612）**
公式依赖“24 小时前总资产”，但数据模型中没有价格快照/历史净值表，也没有说明如何回溯；新用户当天创建时 24 小时前总资产 = 0，除零。且该指标把增资/撤资造成的净值变动也算进“盈亏”，恰好犯了 PRD 自己在第 2 章批评的“无法准确衡量投资回报”的错误，与 ROI 指标的口径互相打架。
**建议：** 明确 24h 盈亏 = 持仓市值变动（剔除法币现金），并新增“价格快照表”（或至少每小时净值快照），首日无快照时显示“--”。

**🔴 R4. API 同步与手动/CSV 数据无合并与去重规则（L461、数据表 1）**
流程图只写了“与本地数据比对，写入新交易”，未定义比对键。transactions 表没有交易所订单号（exchange_order_id/trade_id）字段，无法去重；同一笔交易手动录一次 + API 同步一次就会重复，持仓成本翻倍。另外 Binance 的 myTrades 接口只返回最近 500 条，历史交易必须靠 CSV 补录，文档未提示这一技术边界。
**建议：** transactions 表增加 exchange_order_id；定义去重键（交易所 + 订单号）；明确“余额以 API 为准、历史明细以 CSV/手动为准”的双源策略；API 覆盖余额 vs 重放交易的取舍要写清楚。

**🟡 R5. 交易类型“转账”出现但从未定义（L172 vs L354、L757-772、L663-673）**
用户故事 2.1 描述“买入/卖出/转账交易记录”，但表单只有买入/卖出单选，数据表枚举只有 BUY/SELL，全篇无 TRANSFER 的任何规则。用户实际上有大量站内划转、提币、钱包互转。
**建议：** 要么从 2.1 删除“转账”，要么补充转账类型的字段与成本影响规则（推荐 MVP 明确列为 Out of Scope，后续版本再加）。

**🟡 R6. 手续费币种表里有时表单里没有（L752、L663-673、L300）**
数据表有 fee_currency，用户故事 7.1 也要求“考虑手续费币种（计价币种/基础币种/特定币种）”，但添加交易表单没有手续费币种选择器，手续费设置也只有百分比费率。手续费以基础币种或第三币种（如 BNB 抵扣）计价时无法处理。
**建议：** 表单增加“手续费币种”字段（默认 = 计价币种），并定义手续费如何折算计入成本（汇率或直接用数量）。

**🟡 R7. 平均成本法细则缺失（L26、L354）**
只说“暂定平均成本法”，未定义：手续费是否计入成本基数、成本按账户内合并还是按交易所分开、卖出如何影响平均成本（通常不变）、编辑/删除历史交易后如何整体重算。成本口径不统一，持仓成本、浮盈、ROI 都会漂移。
**建议：** 补一节“成本计算规范”：买入成本含手续费（按手续费币种折算）、卖出不改变平均成本、任何历史交易变更触发全量重放计算。

**🟡 R8. 缺少“已实现盈亏”，且未列入 Out of Scope**
卖出后赚了多少钱、手续费吃了多少，全篇没有任何输出出口。对组合跟踪工具这是高频刚需（用户每次卖出都会看）。既不实现也不说明“为什么不做”，会被用户视为功能缺失。
**建议：** 明确选择：① MVP 补上“已实现盈亏”字段（卖出时以卖出净额 − 对应成本计算）；② 或明确写入 Out of Scope 并给出版本规划。

**🟡 R9. 备份语义冲突（L250 vs L364）**
用户故事 5.2 说备份“当前账户的所有数据”，第 7 章数据管理说备份“整个本地数据库”。多账户产品下两者差异巨大（恢复时是否覆盖其他账户？）。
**建议：** 统一为“备份当前账户全部数据，.cpro 内嵌账户标识；恢复时校验账户匹配”。若产品以后支持整机备份再扩展。

**🟡 R10. 忘记密码无任何交代（全文无）**
本地加密产品“忘记密码 = 数据永久不可恢复”是必然结果，但文档没有任何提示设计。用户设了强密码忘记后，所有资产数据无法解密，会产生极端差评。
**建议：** 创建账户时强制提示“密码是数据唯一钥匙，丢失无法找回”；可选做“恢复短语”（如 12 词助记词加密导出），但至少要写清楚后果。

**🟡 R11. 修改密码与加密体系的连锁影响未定义（L246、L251、L491）**
数据用密码派生密钥加密，备份文件用“备份时密码”加密。用户改密码后：旧数据需全量重加密（成本）、旧备份无法用新密码恢复（体验）、多账户切换的解密逻辑是否受影响，全部未定义。
**建议：** 采用“随机数据密钥 + 密码包裹密钥”结构：改密码只重包裹密钥，不重加密数据；备份内嵌独立密钥并由账户密码包裹，改密后旧备份解密规则写清楚。

### 3.2 安全设计问题

**🔴 S1. “切换账户无需密码”与“无密码无法解密”自相矛盾（L164 vs L246）**
故事 1.3 要求切账户不输密码，故事 5.1 要求密钥与密码强关联、无密码无法解密。技术上两者不可兼得：要么切账户时要密码，要么系统必须持有无需密码即可解密所有账户的密钥材料（等于削弱了隔离）。同时“共享设备多账户”场景下免密切换与“数据隔离保护”的初衷冲突。
**建议：** 密钥架构改为：每个账户数据用独立随机数据密钥加密，数据密钥用“账户密码派生的 KEK”包裹；另在 OS 钥匙串（Windows DPAPI / macOS Keychain / Linux Secret Service）中保存“会话解锁状态”。切账户免密仅限“本机已解锁过”的账户，可设置“切换需重新验证密码”选项。至少让用户在两个需求中二选一，并写进文档。

**🟡 S2. “记住我”以本地保存登录凭据实现自动登录，安全设计薄弱（L153）**
“加密保存登录凭据”意味着本地存有可解密数据的密码等效材料，任意本地攻击者拿到文件即可解锁全部数据，与产品“电脑失窃数据无法破解”的承诺（L249）矛盾。
**建议：** 改为保存“解锁令牌”而非密码：用 OS 钥匙串保管解锁材料，密码本身永不落盘；登出即清除钥匙串中的令牌。

**🟡 S3. 日志可能泄露敏感信息（L318-320 有日志设计，无脱敏要求）**
要求了本地日志用于排障，但未要求对 API 密钥、金额、账户名脱敏。日志文件可被用户导出分享，泄密风险实际存在。
**建议：** 增加“日志中禁止出现密钥明文、密钥哈希及完整 API 响应体”的硬性要求。

### 3.3 使用逻辑问题

**🟡 U1. 双刷新机制关系未定义（L602 每 5 分钟 vs L207-208 可设置 1/5/30 分钟）**
仪表盘“每 5 分钟自动刷新”与设置里“价格刷新频率可调”是两套机制，谁覆盖谁、后台同步周期（30 分钟）与页面刷新如何协调，未说明。
**建议：** 统一为“行情刷新频率（可设置）驱动全部页面”，删除页面级 5 分钟硬编码，或明确页面只重算本地数据、行情按设置拉取。

**🟡 U2. 红绿颜色约定冲突（L200“正数为绿色” vs L602“变化率为红色/绿色”含糊）**
且中英文用户对红涨绿跌/绿涨红跌习惯相反，I18N 既然支持中文，颜色必须可配置或按语言环境默认。
**建议：** 在全局说明中统一规定：“上涨/盈利默认绿色（Western 习惯），设置中提供‘红涨绿跌’开关”，并消除 L602 的含糊表述。

**🟡 U3. 单击 vs 双击打开资产详情不一致（L476 流程图“双击” vs L624、L627 页面描述“点击”）**
**建议：** 统一为单击进入详情（现代桌面习惯），双击为可选快捷方式。

**🟡 U4. 增资/撤资记录不能修改、不能删除（L680-697）**
录错一笔金额或选错类型只能错下去，直接污染投入本金与 ROI。交易记录有修改/删除，资金记录却没有，不对称。
**建议：** 为资金记录补编辑与删除（删除需二次确认），并触发相关指标重算。

**🟡 U5. 删除交易无撤销与确认（L645-651）**
多选删除直接生效，无二次确认、无撤销。
**建议：** 删除前弹出“影响 N 条交易、持仓成本将重算”的确认框；编辑历史交易同理提示影响范围。

**🟡 U6. 时区规则未定义（全文无 UTC/时区字样）**
Binance CSV 是 UTC，手动录入是本地时间，跨时区用户（或导入历史数据）会出现错位，影响 FIFO/成本计算。
**建议：** 统一“存储 UTC、显示按本地时区（或用户设置时区）”，导入时明确解析来源时区。

**🟡 U7. 手续费设置 UI 缺少“交易对级”规则（L307 要求优先级最高 vs 9.11 L724-733 只有全局 + 交易所级）**
故事 7.2 定义了“交易对 > 交易所 > 全局”三级匹配，但 9.11 页面描述只给了全局和交易所级两项，交易对级规则无入口。
**建议：** 9.11 补交易对级规则的表单与列表；或 MVP 砍掉交易对级并同步改故事 7.2（二选一，务必一致）。

**🟡 U8. 饼图口径与总资产不一致（L199、L344-345）**
总资产净值 = 加密资产市值 + 可用现金余额，但饼图只画币种市值占比，存在一块“现金”永远不显示，占比之和与总资产对不上。
**建议：** 饼图增加“现金/其他法币”切片，或注明饼图仅统计加密资产部分。

**🟡 U9. 首次初始化向导缺 API 快速通道（流程图 1 L396-405 vs 激活指标 L132）**
激活指标以“添加第一笔交易 **或** 关联第一个 API”衡量，但初始化向导只给“手动添加 / CSV 导入”两条路，最省力的 API 路径反而没有入口。
**建议：** 向导第三步增加“关联交易所 API（推荐）”选项。

### 3.4 易用性问题

**🟢 E1. 交易管理用“选择框 + 按钮”编辑单条记录很笨重（L644）**
单条编辑也要先勾选再点按钮；建议行内悬浮“编辑/删除”操作，多选保留用于批量删除/导出。
**🟢 E2. 缺桌面级体验**：系统托盘驻留、最小化后台同步、开机自启、同步完成通知、全局快捷键等桌面应用标配均未涉及。用户画像“间隔式打开使用”恰恰需要托盘+定时同步兜底。
**🟢 E3. 恢复数据前只给警告，未展示备份内容摘要**。建议恢复前显示备份文件的账户名、备份时间、交易/资金记录条数，帮助用户确认选对了文件。
**🟢 E4. 8 位小数精度对小币种可能不够（L50）**：SHIB 等微小单价 8 位可能全为 0。好在“用户可在设置调整精度”，建议把默认精度改为“金额 8 位 + 数量按币种自适应（有效数字 8 位）”。
**🟢 E5. 无遥测的隐私承诺应显式写出来**（隐私优先产品的重要卖点与合规点）：明确“本产品不含任何遥测/统计上报”，并写进隐私政策链接。
**🟢 E6. 导入预览可更强**：除了预览行与重复提示，建议显示“导入后持仓将变为 X、新增 N 条”的影响摘要。
**🟢 E7. 流程图 2 的“选择手续费计算方式 → 点击自动计算？”两步冗余**，可简化为“手续费：手动输入 / 自动计算”单选。

### 3.5 数据模型问题

**🔴 D1. 主键类型与引用类型不一致**：accounts.id 是 Integer 自增，而 transactions/capital_flows/api_keys 的 account_id 是 UUID（L742、L761-772、L783、L796），无法外键关联。统一为 UUID 或统一为 Integer。
**🔴 D2. capital_flows.account_id 描述是复制粘贴错误**：写成“关联到用户账户的ID (全局设置此项为空)”（L796），后半句属于 settings 表。
**🟡 D3. 缺表/缺字段**：
- 无“价格快照/净值历史表”→ 24h 盈亏无法实现（同 R3）；
- 无“手续费费率规则表”→ 6.3/9.11 的功能无落点；
- transactions 无 exchange_order_id → 无法去重（同 R4）；
- 无会话/解锁状态表 → 免密切换逻辑无落点（同 S1）；
- 无数据库 schema 版本字段 → 本地应用升级迁移策略缺失（备份文件有版本，数据库自身没有）。
**🟡 D4. transactions 表未标 fee 的计价与含费成本字段**：建议增加 fee_in_quote/含费成本等派生字段规范，或明确“成本一律含费”的计算函数。

### 3.6 成功指标问题

**🟡 M1. WAU>30% 且 MAU>40% 与画像矛盾（L133 vs L112）**：WAU/MAU 比高达 75%，而画像明确“用户间隔式打开使用”。月度型工具（如记账、报税）的 WAU/MAU 通常 20-40%。建议 WAU 降到 15-20%，或改为“月活跃中每周打开≥1 次比例”。
**🟡 M2. “数据准确性反馈：手动修正频率<5%”不可测量（L140）**：5% 的分子分母是什么（修正次数/总记录数？发生修正的用户占比？）没有定义。建议改为“单月内发生手动修正的用户占比 < 10%”或直接删掉，改用数据质量抽查。
**🟡 M3. 满意度 80% 的收集口径模糊**：应用内反馈 + GitHub/Reddit 如何汇总未定义，建议以应用内 NPS 或 5 星评分为准。
**🟢 M4. 缺过程指标**：CSV 导入成功率、API 首次连通率、备份功能使用率等北极星之下的漏斗指标没有，建议补 2-3 个。
