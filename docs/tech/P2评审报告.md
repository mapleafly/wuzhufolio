## 二、架构合理性分析（正面结论）

1. **分层与模块边界合理**：UI（Compose）→ 应用（用例）→ 领域（纯 Kotlin）→ 基础设施四层，依赖方向单向；领域层无 IO 可单测，M4 引擎以黄金用例 1–12 作硬验收，工程化程度高。
2. **ReplayEngine 单引擎设计是最大亮点**：交易/资金/校准/导入/恢复五类入口复用同一全量重放引擎，与共享规范 §2「任何历史记录的新增/编辑/删除均触发全量重放」精确对齐；锚点语义、负持仓校验、恒等式保持全部落到引擎契约，从根上避免了多入口口径漂移。
3. **并发模型与需求逐字对齐**：单写队列（Mutex）+ WAL + busy_timeout + 读写连接分离，与 PRD §10 注 / 共享规范 §7 一致；MVP 不引入乐观锁的取舍正确。
4. **两类 API 隔离落实到三层**：行情（MarketDataClient）与交易（ExchangeAdapter）接口、调度、日志各自独立，满足硬约束 4；ADR-003 的额度治理/429 退避/24h 同源快照闭环完整。
5. **安全设计纵深正确**：整库密钥随机入钥匙串（文件窃取不可解）+ 凭证字段级 DEK（支撑 .cpro 解密→重加密语义）+ 密钥材料擦除 + 日志脱敏，与硬约束 1/2/3 逐条对应；改密只重包 DEK 不重加密数据的设计正确。
6. **技术栈检验通过**（详见第五节逐项）：Kotlin + Compose Desktop 落地链条完整（官方模板基座 → Gradle/version catalog → Koin/StateFlow → jpackage），每项选型在 JVM 生态均有可用实现，ADR 对两大已知风险（读屏弱于 Web、SQLCipher 驱动社区维护）均显式登记并给出缓解与升级路径。

## 三、发现问题

### F1【阻断 · 文档间矛盾】行情 Key（CG/CMC）的加密归属三处不一致

- **矛盾点**：
  - `data-model.md` §2.3 注 + `ADR-003` 备注：CG/CMC Key 存 `settings` 表，「按 DEK 字段级加密存储」；
  - `ADR-002` 决策 + `data-model.md` §5 + 共享规范 §7 + PRD §10 注：**字段级加密仅限 api_keys 四列**（api_key/secret_key/passphrase/extra），其余列可索引/排序。
- **后果**：
  1. settings 是 key-value 表，对个别 value 做 DEK 加密破坏了 ADR-002 自己声明的加密边界，且加密列不可索引/排序与 settings 按键检索冲突；
  2. **备份语义断裂**：ADR-005 的「解密 → 目标账户 DEK 重加密」只覆盖 api_keys；若 settings 里存了源账户 DEK 加密的行情 Key，跨账户/新设备恢复后该密文**永远解不开**；
  3. 行情 Key 是账户级还是全局（account_id NULL）未定义——若为全局设置，用哪个账户的 DEK 加密？全局设置又不进备份，语义更加含混。
- **建议方案（供人工拍板）**：
  - **方案甲（推荐）**：行情 Key 视为**应用级秘密**（非账户资产），用与 DB 密钥同级的「设备密钥」（OS 钥匙串保护）加密后存全局 settings，**不进 .cpro 备份**（恢复后用户重填一次即可，成本极低，且避免备份文件扩大敏感面）；
  - 方案乙：扩展字段级加密白名单至这两个 settings key，并联动修订 ADR-002、ADR-005（备份解密→重加密范围）、共享规范 §7（需走规范修订流程升版本）。
- **要求**：无论选哪个方案，ADR-002/003/005 与 data-model 四处口径必须收敛一致后才能进 P3（M1 存储加密是第一批任务）。

### F2【重要 · 技术可行性】Binance 现货无全账户成交端点，同步缺 symbol 枚举策略

- **事实**：`GET /api/v3/myTrades` **必传 symbol**（现货无账户级成交端点），单次权重 10；现货交易对约 2,000+。ADR-004 与 api-contracts §2 的 `fetchTrades(since, cursor)` 签名未体现这一点。
- **后果**：若实现时按 exchangeInfo 全量交易对逐一拉取，一次全量同步 = 数万次调用，必然触发 -1003/429 乃至 418 封禁，T6.2 验收标准无法达成。
- **建议**：ADR-004 补「同步范围收敛策略」：候选 symbol = （账户余额非零资产 × 常见 quote 可组成的 pair）∪（本地已同步过的 pair）∪（用户手动添加的 pair），逐 symbol 增量（fromId）拉取；T6.2 验收标准增加「单次同步调用数 ≤ N（权重预算内）」条款。

### F3【重要 · 任务结构】M12「大整合」式 UI 后置，与 P4 人工门协议冲突且风险后置

- **现状**：M12（十八页 + 异常态 + a11y + i18n）依赖 M2–M11 全部完成，集中在最后 4 个任务。
- **问题**：
  1. AGENTS.md P4 要求**逐模块人工测试**——M2–M10 无任何 UI，人工门只剩单测可看，「人工测试该模块」形同虚设；
  2. 与 P1 原型截图的走查对比全部压在 M12，视觉/交互偏差发现即返工，集成风险后置；
  3. M12 四个任务承接 18 页 + 双主题 + 全量异常态 + i18n，工作量明显低估。
- **建议**：改**垂直切片**——M7/M8/M9/M5/M6 等模块自带其 Compose 页面（P1 原型已提供完整视觉与交互基准，逐页还原本就是既定方式），M12 退化为「导航/跨页一致性整合 + 双主题/对比度总验 + i18n/a11y 收尾 + 全量异常态走查」。依赖图相应把 UI 依赖前移到各模块。

### N1【轻微 · schema 缺陷】三处唯一性约束在 SQLite 下不成立

1. `settings` 的 UNIQUE(account_id, key)：SQLite 中 NULL 在 UNIQUE 里视为互不相等，**account_id NULL（全局设置）时同 key 可重复插入**。建议改用表达式唯一索引 `UNIQUE(COALESCE(account_id, 0), key)` 或两个部分唯一索引（`WHERE account_id IS NULL` 对 key；`WHERE account_id IS NOT NULL` 对 (account_id, key)）。
2. `transactions` 去重键 (exchange, exchange_order_id) 仅声明为普通索引，手动录入 NULL 订单号场景下也无法唯一约束；建议落为部分唯一索引 `UNIQUE(account_id, exchange, exchange_order_id) WHERE exchange_order_id IS NOT NULL`，从数据库层防并发漏重。
3. `price_snapshots`「每 (coin_id, fiat) 每小时最多一条」未说明实现机制；建议唯一索引（coin_id, fiat, 小时桶表达式）或应用层 upsert，并在文档注明。

### N2【轻微 · 性能细节】password_hash 与 KEK 派生关系未定义，有 2× KDF 风险

PRD §12 给登录解密的预算是 **≤2s**。若实现时先跑一次 Argon2id 校验 password_hash、再跑一次派生 KEK，耗时直接翻倍。建议 ADR-002 明确：**单次 Argon2id 派生 KEK；用 KEK 解包 wrapped_dek 的 GCM tag 校验即完成密码认证**（密码错误必然 tag 校验失败）；password_hash 字段可退化为 KEK 的派生校验值（如 SHA-256(KEK ‖ "verify")），零额外 KDF 成本，仍满足 PRD「password_hash 不可逆、仅登录校验」。

### N3【轻微 · 文档准确性】「macOS universal」并非 PRD 要求，待确认差异实为 1 处

ADR-006 风险表与 STATUS.md 把「macOS universal 单包」列为与 PRD §12 的口径差异。**PRD §12 原文只要求「macOS 12+（Apple Silicon / Intel）」**，并未要求 universal 单包——jpackage 按架构出 x64 + arm64 两包即满足 PRD。真正的口径差异只有 **Linux Flatpak** 一处（PRD 明示 AppImage + Flatpak）。建议修订 ADR-006 与看板措辞，人工待确认项由两处减为一处（避免过度请示）。

### N4【轻微 · 实现提示，P3 验证项补强】

1. **Ktor + 系统代理**：Ktor CIO/Apache 引擎不自动遵循 JVM `ProxySelector`，需显式装配；PRD 故事 4.2 要求自动检测系统代理，建议直接在 ADR-001/003 指定 **OkHttp 引擎**（原生支持 ProxySelector），或 P3 明确引擎选型 + 代理装配并列入冒烟。
2. **SQLCipher 密钥注入时序**：xerial 系驱动要求 `key` 在连接建立时以连接属性（或首条语句）设置；「连接后执行 PRAGMA key」在驱动初始化已触碰 DB（如设置 journal_mode）时会失败。ADR-002 表述建议改为「经连接属性注入密钥」，P3 锁版验证覆盖。
3. **SQLCipher + WAL 组合**：SQLCipher 支持 WAL 但与加密页交互有版本差异，建议把「WAL 在 SQLCipher 下生效」明确列入 T1.1 三平台验证清单。

### N5【轻微 · 依赖治理】AGPL 兼容性核验建议点名具体库

ADR-006 已要求依赖许可证核验；建议点名：**argon2-jvm（LGPL-3.0）**、**javakeyring**、**dorkbox SystemTray/Notify**、**Willena/sqlite-jdbc-crypt**（及其捆绑的 SQLCipher/openssl 原生库）、BouncyCastle。P3 锁版时随 version catalog 出具依赖许可证清单（T0.1 验收标准可增补此条）。
