# ADR-006 构建与分发（AGPL-3.0 · GitHub Releases · jpackage 三平台签名/公证）

- **状态**：**人工拍板采纳**（2026-08-31，含 Flatpak 口径：本轮先 AppImage/.deb/.rpm，Flatpak 走 Flathub manifest 并行推进、P7 前评估是否为硬门槛）
- **日期**：2026-08-31（本轮适配 Kotlin + Compose Desktop）
- **决策类型**：架构级
- **需求回溯**：PRD §12（OS 矩阵/签名公证/更新策略/开源与分发 D1）、PRD §4（成功指标）、`桌面端prd-三大决策分析.md`（D1）

---

## 背景

PRD §12 已定：正式发布须完成 macOS 公证与 Windows 代码签名；MVP 不内置检查更新（网络白名单不变）；开源（D1：源码公开 + GitHub Releases + AGPL-3.0）；Linux 通过 AppImage + Flatpak 分发。本 ADR 在 Compose Desktop 栈下把构建、CI、签名/公证与分发落为可执行方案，并对「AppImage/Flatpak」给出与 jpackage 的适配说明。

## 决策

### 1. 构建产物（Compose Gradle 插件 → jpackage）

| 平台 | 产物 | 说明 |
|------|------|------|
| Windows | `.msi`（主）+ `.exe` | jpackage `packageMsi` |
| macOS | `.dmg` + `.pkg`（可选） | jpackage `packageDmg`；x64 与 arm64 各出（universal 见风险） |
| Linux | `.deb` + `.rpm`；AppImage 追加 | jpackage `packageDeb`/`packageRpm`；AppImage 用 appimagetool 包 jpackage app-image |

### 1.1 原生运行时分发模型（2026-08-31 人工确认口径）

- **「打包成本地 exe、脱离系统 Java 环境」= jpackage 捆绑私有 JRE**：安装包内嵌 jlink 裁剪的私有运行时，用户机器无需安装任何 Java；exe/dmg/deb 均为原生启动器/安装器。此为既定方案，体积代价（~80–150MB）已在 ADR-001 风险表登记并接受。
- **与托盘/通知无冲突**：`java.desktop` 模块（含 AWT SystemTray）是 Compose Desktop 窗口系统本身的依赖，必然包含在捆绑运行时中——托盘/通知在 exe 内正常工作；托盘首选 Compose Tray API（ADR-001），AWT 仅为底层实现。
- **明确排除 GraalVM Native Image 纯原生编译**：Compose Desktop 渲染栈（Skiko + AWT/Java2D + Swing 互操作）无法 AOT 为原生镜像；坚持纯原生二进制需推翻 ADR-001 整个技术栈，不采纳。
- 对其他方案无冲突：SQLCipher 原生库随包按平台分发、javakeyring（JNA）、Ktor/OkHttp、签名/公证、CI 矩阵均不受本模型影响。

### 2. 签名与公证

- **macOS**：Developer ID 证书签名 + `notarytool` 公证 + `stapler` 钉装；发布硬门槛（PRD §12）。
- **Windows**：代码签名证书（OV/EV）签名，建立 SmartScreen 信誉；证书成本入 P7 计划。
- **Linux**：`.deb`/`.rpm` 签名；AppImage 附加；Flatpak 走 Flathub 流程（见风险）。

### 3. CI（GitHub Actions）

- 矩阵：`windows-latest` / `macos-latest`（x64 + arm64）/ `ubuntu-latest`。
- 流水线：`./gradlew test`（JUnit5 + Compose UI 测试）+ `detekt`/lint → 三平台 `./gradlew package*`（冒烟）→ 发布时签名/公证 + 上传 GitHub Releases。
- 密钥：签名证书/Apple ID 经 GitHub Secrets（CI 专用），禁止入库；本地开发不签名。
- AGPL-3.0：根 `LICENSE`（AGPL-3.0）+ 依赖许可证清单（P3 T0.1 随 version catalog 出具并逐项核验兼容；重点核验：argon2-jvm（LGPL-3.0）、javakeyring、dorkbox SystemTray/Notify、Willena/sqlite-jdbc-crypt（含捆绑 SQLCipher/OpenSSL 原生库）、BouncyCastle、OkHttp、Ktor、Exposed——评审 N5）。

### 4. 分发与更新

- GitHub Releases 产物 + SHA256 校验和 + CHANGELOG。
- 不内置检查更新（PRD §12）；关于页显示版本号 + 官方发布渠道链接（浏览器打开）。
- 下载量/星数/Fork 作为外部指标（PRD §4）。

## 选项

| 选项 | 优点 | 缺点 |
|------|------|------|
| **GitHub Actions + jpackage + 公证/签名（选定）** | 与 PRD §12 对齐；Compose 插件原生；可自动化 | 公证/签名证书付费；AppImage/Flatpak 需追加步骤 |
| 仅本地手动构建 | 无 CI 成本 | 三平台人工构建低效、易漏签名 |
| 内置检查更新 | 用户便利 | 违反 PRD §12 网络白名单，不采纳 |

## 理由

1. Compose Desktop 官方分发路径即 jpackage，与 ADR-001 技术栈一致。
2. 逐字对齐 PRD §12 的签名/公证与无检查更新要求。
3. CI 矩阵把「构建、测试绿、签名合规」做成可重复验证，支撑 P3 DoD 与 P7 发布。

## 风险

| 风险 | 缓解 |
|------|------|
| macOS 双架构出包 | jpackage 默认按架构出包，x64 + arm64 两包即满足 PRD §12「Apple Silicon / Intel」支持矩阵（PRD 未要求 universal 单包，2026-08-31 评审 N3 核实）；universal 合并包仅作 P7 可选优化，非合规项 |
| **Linux Flatpak（口径已拍板 2026-08-31）** | jpackage 不原生产出 Flatpak；需另写 flatpak manifest + runtime。**本轮先 AppImage（appimagetool 包 app-image）+ .deb/.rpm**，Flatpak 走 Flathub 流程并行推进、P7 前评估是否为硬门槛——此口径已经人工拍板确认 |
| 公证/签名证书成本与周期 | P7 计划预留；MVP 期用未签名产物内部验收 |
| JRE 体积 | jlink 裁剪 JRE 减小体积（P7） |
| CI 凭据泄露 | GitHub Secrets + 专用签名身份，仓库不含凭据 |

## 备注

- 签名/公证具体命令与证书申请留 P7；P3 只搭 CI 矩阵与本地未签名构建链路。
- 移动端打包不在本决策范围（AGENTS.md §4）。
- **与 PRD §12 的口径差异仅 Linux Flatpak 一处**（macOS 双架构出包已核实满足 PRD，2026-08-31 评审 N3）；**Flatpak 口径已人工拍板（2026-08-31）**：本轮先 AppImage/.deb/.rpm，Flathub manifest 并行推进、P7 前评估。
