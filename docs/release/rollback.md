# WuZhuFolio 回滚方案（rollback.md）

> **阶段**：P7 发布 · **适用版本**：0.1.0（首个公开发布）· **文档日期**：2026-09-22
> **配套**：`release-plan.md`（发布步骤）、`signing-notarization.md`（签名/公证）、`docs/release/CHANGELOG.md`（版本差异）
> **DoD 对照**：`AGENTS.md §4 P7` —— 「回滚步骤可执行」。

---

## 0. 一句话结论

WuZhuFolio **不内置自动更新**（PRD §12）：发布动作本身**不会**触达任何已安装用户，用户升级永远是手动下载安装。
这使回滚的风险面很小——**「撤回发布件 + 发布更正说明」在绝大多数情况下就已完成回滚**；
只有「用户已升级且新版损坏其数据」这类情况才需要 §4 的数据级恢复。

---

## 1. 回滚分级与决策矩阵

| 级别 | 触发情形 | 动作 | 完成时限 | 影响面 |
|------|----------|------|----------|--------|
| **R0 撤回发布件** | 产物错误（传错文件、校验和不符、含调试件）、签名缺失导致无法安装 | Release 转 draft 或删除附件 → 修正后重发 | 立即（分钟级） | 仅未下载者受益；已下载者不受影响 |
| **R1 标记版本不可用** | 已确认存在阻断性缺陷，但用户数据未受损 | 保留 Release 并置顶醒目警告 + 发布 `0.1.1` 修复版；**不删除历史版本**（用户可能已依赖） | 小时级 | 全量用户（靠公告触达） |
| **R2 用户侧降级** | 新版在个别环境不可用（如启动失败），用户希望退回旧版 | 卸载新版 → 安装旧版 → 数据目录处理（§4.2） | 用户自助 | 单用户 |
| **R3 代码回滚重出包** | 缺陷根因在代码、需回退到已知良好提交 | `git revert`（**不用** `reset --hard`）→ 重新走 CI → 出补丁版 | 天级 | 需重新测试 |

### 1.1 触发阈值（什么情况必须回滚）

| 缺陷类型 | 处置 |
|----------|------|
| 启动即失败（`Failed to launch JVM` / 白屏 / 崩溃）→ 阻断 | **R1 + R3**：立即公告 + 出补丁版 |
| **数据损坏或丢失**（导入/恢复/迁移导致账本被破坏） | **R1 + R3**，最高优先级；同时给出 §4.3 恢复路径 |
| 加密或隐私失效（明文落盘、越白名单出站、密钥泄露） | **R1 + R3**（`AGENTS.md §1.1` 硬约束级） |
| 签名/公证缺失导致系统拦截 | **R0**：补齐签名后重发，不视为代码缺陷 |
| 单页显示错位 / 文案瑕疵 / 非阻断交互问题 | **不回滚**：计入下一补丁版（P8 迭代） |
| 上游限制（如 jpackage 非 ASCII 路径） | **不回滚**：属已知限制，靠文档提示与便携版缓解 |

## 2. 0.1.0 的特殊说明（首个公开版本）

- **无上一公开版本可退**：R2「用户侧降级」在 0.1.0 阶段**不适用**（没有 0.0.x 公开版）。
  - 若用户已装 0.1.0 且希望「回到没装的状态」→ 卸载 + 删除数据目录（`user-guide.md §11`）。
  - 开发期内部构建（P4/P5/P6 期间的 `createDistributable` 产物）**不属于**公开版本，不提供回滚目标。
- **0.1.0 的回滚 = R0/R1/R3**：撤回或标注发布件、修代码、出 `0.1.1`。
- 首个版本的 `upgradeUuid` = `6f2a1c9e-8b74-4d3a-9c1f-2e5b7a0d4c88`（`app/build.gradle.kts`，**发布后不得再改**，否则 MSI 无法走升级路径）。

## 3. R0 / R1：发布件层面的回滚（命令可直接执行）

```bash
# --- R0：撤回（未发布时改 draft；已发布可删附件或整条删除）---
gh release edit v0.1.0 --draft                 # 退回草稿（页面仍可见但标记为 draft）
gh release delete-asset v0.1.0 <文件名>        # 只删单个错误产物
gh release delete v0.1.0 --yes                 # 整条删除（谨慎：会同时删 tag，需 --cleanup-tag 才删 tag）

# --- R1：保留版本但标注不可用 ---
gh release edit v0.1.0 --notes-file docs/release/rollback-notice-v0.1.0.md   # 置顶警告文本
# 警告文本至少写明：受影响版本 / 现象 / 是否影响数据 / 建议动作 / 修复版发布时间

# --- R3：代码回滚并重出补丁版（示例：回退单个提交）---
git revert --no-edit <bad-commit-sha>          # 生成反向提交，保留历史（禁止 reset --hard 后强推）
git push origin main
git tag -a v0.1.1 -m "WuZhuFolio 0.1.1 —— 修复 <问题>"
git push origin v0.1.1
# 随后按 release-plan.md §4/§5 重新出包、签名、发布
```

> **为什么禁止 `reset --hard` + 强推**：AGPL-3.0 开源仓库的历史即审计线索；强推会破坏用户与打包者的可信基线，也会让已下载版本的溯源断链。

## 4. R2：数据层面的恢复（用户侧，最关键的一节）

### 4.1 升级前的自保动作（写进用户指南的推荐做法）

```bash
# 升级前：整目录冷备份（数据目录默认 ~/.wuzhufolio）
cp -a ~/.wuzhufolio ~/.wuzhufolio.bak-$(date +%Y%m%d)
# 或者（推荐给普通用户）：应用内「数据管理 → 导出 .cpro 备份」
```

### 4.2 降级时的数据兼容性（**已核对代码事实**）

- 数据目录内容：`wuzhufolio.db`（SQLCipher 加密整库）、`master.key`（设备密钥，0600）、`logs/`。
- 数据库带 `schema_version` 表；`Migrator.migrateToLatest()` 的语义是**只升不降、且不对「库版本高于程序版本」报错**
  （源码：`data/src/main/kotlin/com/wuzhufolio/data/db/Migrator.kt` —— `if (migration.version <= version) continue`，无上限校验）。
- **推论（降级可行但有前提）**：
  1. 用**旧版程序**打开**新版程序迁移过的库**：不会因版本号被拒，旧版按自己的迁移集运行；新增的表/列被忽略，**通常可用**；
  2. 但若新版本**改变了既有列的含义或派生口径**，旧版可能按旧口径重算 → **展示结果可能与升级后不一致**；
  3. 因此**官方支持的回退路径是「用旧版 + 升级前的数据副本/备份」**，而不是「旧版直接读新库」。

### 4.3 推荐回退步骤（用户侧）

1. **不要先卸载**：先确认数据目录位置并整目录复制一份（§4.1）。
2. 卸载当前版本（Windows：设置 → 应用 → WuZhuFolio；macOS：拖出 Applications；Linux：包管理器卸载 / 删便携目录）。
3. 安装/解压旧版（或改用便携版，避免安装器差异）。
4. 数据处置二选一：
   - **A（推荐）**：把当前 `~/.wuzhufolio` 移走（`mv ~/.wuzhufolio ~/.wuzhufolio.new`），把升级前的副本放回原位（`mv ~/.wuzhufolio.bak-YYYYMMDD ~/.wuzhufolio`）→ 旧版读到的是它认识的数据。
   - **B（无副本时）**：启动旧版并**先导出一次 `.cpro` 备份**确认数据完整；如出现展示异常，改用「先新建账户 → 再恢复备份」重建。
5. **`master.key` 必须与库成对**：二者不匹配会得到「无法解锁本地数据库」（类型化拒绝，不会静默损坏）。若只恢复了库而密钥是新的 → 用 §5 的判据处理。

### 4.4 Windows 安装形态提示

per-machine 安装（`C:\Program Files\WuZhuFolio`）与历史 per-user 安装**不属同一升级路径**：回退到 per-user 时代产物前须先卸载。
`upgradeUuid` 未变，故 **0.1.0 → 0.1.x 走正常升级**，无需卸载。

## 5. 回滚判据与验证清单

回滚完成后必须逐项验证（每条都要有结论，不接受「应该没问题」）：

- [ ] `gh release view v0.1.0` 的状态与说明符合预期（draft / 已标注警告 / 已删除）。
- [ ] 修复版 `SHA256SUMS` 与 Release 附件一一对应，`sha256sum -c` 通过。
- [ ] 修复版在其目标平台的**首次启动冒烟**通过（无 `Failed to launch JVM`；日志仅脱敏信息）。
- [ ] 数据回归：用 0.1.0 期间产生的 `.cpro` 备份在修复版上**完整恢复**（行数、总资产、ROI 与备份摘要一致）。
- [ ] `~/.wuzhufolio` 权限仍为 700、`master.key` / `wuzhufolio.db` 为 600。
- [ ] 出站仍只有三个白名单主机（可复用 `scripts/outbound-capture-proxy.py`，见 `security-checklist.md §8`）。
- [ ] 发布说明/公告已写明：受影响版本、现象、数据影响、用户该做什么、修复版版本号。
- [ ] `docs/release/CHANGELOG.md` 已追加修复版小节（不修改历史小节）。

## 7. 不可回滚 / 不可恢复清单（必须让用户知道）

| 项 | 说明 |
|----|------|
| **忘记备份密码** | `.cpro` 载荷为本机外唯一密文副本；密码不可找回，无后门（`user-guide.md §4/§10`）。 |
| **设备密钥与库同时丢失** | `master.key` 不在备份包内；换机迁移必须走 `.cpro`（导出时用备份密码重新加密）。 |
| **已删除的账户/交易** | 应用内删除即刻生效且无回收站；只能靠删除前的备份恢复。 |
| **已加密的旧库 + 新设备密钥** | 表现为「无法解锁本地数据库」，无法绕过（设计如此）。 |
| **已安装用户的旧版程序** | 不内置自动更新、也没有内置降级器；须用户手动下载（这也是 0.1.0 发布风险极低的原因）。 |
